## Claims

- C1 (source; S1): In table QA queries, the selected column (asked for) and the WHERE condition values (supplied to select rows) are separate roles in the query form.
- C2 (interpretation; S2, S6): Exact-text matching judges text, not meaning, so a short asked-for value whose text also appears in the question or in another fact cannot be checked on its own.
- C3 (source; S3): Lines 89-90 decide 'supplied by the question' and 'redundant' by substring tests against the whole question and the other found values, and _coverage ignores field names and question words before counting what is missing.
- C4 (interpretation; S3, S4): Rows 377 (데이터 vs '데이터 모델 검증') and 343 (데이터 inside '데이터 설계 요구사항') lose asked-for classifications through the same mechanisms as row 379 and are not yet reported.
- C5 (interpretation; S3, S5): The fixes failed because each changed only the filter the reviewer named, while the coverage guard ignores the same text the remaining filters drop and the test pins only named rows; a check over all of dev on labelled answer values plus a per-occurrence supplied/asked-for test addresses the cause.

## Core theory

In table question answering, a query has two roles that a value can play. The selected column holds what is asked for. The WHERE conditions (column, op, value) hold what the question supplies to pick the row (WikiSQL form: 'SELECT agg_op agg_col from table WHERE cond1_col cond1_op cond1 ...'). A value's role comes from its place in the question's structure, not from whether its words occur in the question. Separately, lexical matching is a weak test of meaning (Kamalloo et al. 2023): it judges by exact text, so a short value shared with the question text cannot be told apart from a copy of the question by text alone.

## Applicability

rag/validation/validation.py:85-92 builds found = values that appear in the answer and do not appear in the question, then drops any found value contained in a longer found value, then filters by _coverage >= 0.6. Lines 89 and 90 decide 'supplied' and 'redundant' by plain substring tests against the whole question and the other values. These should be tests on where the value appears in the answer. A value is supplied by the question when every one of its occurrences in the answer sits inside a longer span copied from the question; it is redundant when every occurrence sits inside a longer found value. One cheap way to test this: remove whitespace from answer and question, and for each occurrence check whether extending it by one character left or right still gives a substring of the question (or of the longer value). Row 379: occurrence ':기능지' has neither ':기능' nor '기능지' in the question, so it is asked for. The second occurrence '반기능' is in the question, so it is copied. Row 377: ':데이터' and '데이터참' are not in the question, so 데이터 is asked for. Row 343: '데이터;' appears outside '데이터설계요구사항', so it is kept. A prose copy such as 'DAR-002요구사항…' when the question says 'DAR-002 요구사항에…' extends into the question text, so it stays excluded. _coverage (lines 72-74) must stop ignoring question words that are context values found in the answer; otherwise the guard keeps missing this class of loss.

## Hypothesis

The extractor never identifies which values are asked for. It only removes values, using text features as proxies for 'not asked for': first-cell label (field_names), substring of the question, substring of a longer found value, length, and the quantity form. The only guard against over-removal (_coverage) ignores the same text: field names and question words. Any asked-for value removed by those filters is therefore invisible both to the guard and to the row-pinned test, and every fix that changes one filter leaves the others. Rows not yet reported confirm this. Row 377 loses classification 데이터 to the question filter (the question says '데이터 모델 검증'). Row 343 loses classification 데이터 to the containment filter ('데이터 설계 요구사항'). The question filter is also a bag-of-text test: it asks whether the value's text appears anywhere in the question, not whether the question supplies that value as a condition.

## Counterevidence

- Only 21 of 71 multi_hop dev answers use the 'label: value' form (count from a regex over dev.jsonl). For prose answers the occurrence test is the only signal, and it has not been run on the data.
- An answer can restate a supplied value with a different particle ('SFR-003은' when the question says 'SFR-003인'). Neither one-character extension is then in the question, so the supplied value would be kept as a fact that any copy of the question matches.
- Keeping 기능 / 데이터 as facts is a weak check under the literal matcher: _key_fact_ratio(['기능'], '지도기반 기능 두 가지는 …') is 1 for an answer that only repeats the question. Keeping the value satisfies the reviewer's request but does not make it independently checkable. For row 343, 데이터 is matched anyway by any answer containing '데이터 설계 요구사항'.
- Kamalloo et al. report lexical matching failing in the other direction (missing correct answers that are worded differently), not crediting copies of the question; the source supports only the general weakness of exact-text matching.

## Alternatives

- Positive label signal from the question (WikiSQL-style): a value is asked for when the question names its row label (for example the label's last word '분류', '고유번호', '세부내용'). Not first, because the question can name a label as a condition too ('고유번호가 SFR-003인', row 353), and labels are paraphrased ('이 요구사항의 분류' vs '요구사항 분류').
- Positive answer signal: a value the answer states as 'label: value' is asked for. Precise where it applies, but only 21 of 71 multi_hop answers have that form. Use it as the cross-dev test, not as the rule.
- Drop any row where an answer value shared with the question (or contained in another value) would be dropped. Honest and cheap, and matches the round-3 decision to drop under-covered rows, but it shrinks dev further and does not preserve values as the reviewer asked. Keep it as the fallback if the occurrence test misclassifies values on dev.
- LLM decomposition of answers into asked-for parts: paid on the shared OpenAI key (cost estimate and approval needed first) and nondeterministic. Not for this cycle.
- Per-hop structure emitted by golden_pipeline for multi_hop rows (structure is {} today): the cleanest long-term source of asked-for values, but it needs a paid regeneration and belongs to another module.
