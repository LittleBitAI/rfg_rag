## 답 · 2026-10-18 11:09 · unverified

I recommend **one shared offline benchmark, run in two stages**: first compare retrieval methods with KURE-v1 fixed; then compare embedding models primarily by their performance alongside Kiwi BM25. This gives you both answers without confusing tokenizer changes with embedding changes.

The project already has deterministic retrieval metrics and API-free retrieval reruns. The recent Kiwi work improved its tokenizer, but it compared Kiwi variants—not the five methods you now want. Reuse that foundation.

| Stage | Comparison | Keep fixed |
|---|---|---|
| 1: Retrieval methods | Standard BM25; KURE-v1 alone; Kiwi BM25; Kiwi + KURE-v1; standard BM25 + KURE-v1 | Dev questions, chunks, labels, candidate limit, fusion formula |
| 2: Embedding models | Each local model alone and with Kiwi BM25 | The selected Kiwi tokenizer and the same evaluation inputs |

Use original dev questions throughout, with no rewriting, generation, judges, embedding APIs, or telemetry calls. Build experiment indexes separately from the active index. Each embedding model needs its own document vectors and appropriate query/document formatting.

There are three details that materially affect the conclusion:

- **Label coverage limits the verdict.** The latest tokenizer experiment scored document retrieval on 376 answerable questions with golden evidence, but chunk retrieval on only 186 fully labelled questions. It excluded 190/376 questions (50.53%) from chunk scoring; comparison, multi-hop and table questions were especially underrepresented. Recheck those mappings against the frozen corpus, and describe the winner as best on the eligible dev subset—not conclusively best across every question type.
- “Standard BM25” needs a tokenizer definition. BM25 is the scoring method; Kiwi changes its input tokens. The earlier Kiwi baseline was already morphological analysis, so it is not a non-Kiwi baseline.
- Setting `dense_weight` to zero or one does not create a completely pure method: exact requirement-code promotion still runs, and quantity-filter questions can take another path. Decide whether the main comparison measures isolated retrieval methods or the deployed pipeline.

For measurements, I recommend:

| Measurement | Meaning |
|---|---|
| Document/chunk Recall@5/10/20 | Per question, gold documents/chunks found divided by all gold documents/chunks; averaged over fully labelled eligible questions |
| Document/chunk MRR@5/10/20 | Reciprocal position of the first gold hit, or zero; averaged over the same eligible questions |
| Evidence Coverage and full coverage | Gold chunks included in the packed context divided by all gold chunks; also the fraction of eligible questions receiving every gold chunk |
| Retrieval latency p50/p90 | Median and 90th percentile in milliseconds per query, including query embedding through returned context |
| Resource costs | Index-build seconds, index size, and peak memory on the same machine |

Measure latency after warm-up, with batch size one and repeated passes; exclude model loading and index construction from query latency and report them separately. Do not cache query embeddings in the timed path. Freeze the context-budget tokenizer across models, because the current implementation uses the embedding tokenizer: otherwise “2,500 tokens” changes meaning between candidates.

For model selection, use **Kiwi-hybrid chunk Recall@10 as the primary quality criterion**, with Recall@20, multi-evidence coverage, topic regressions and p90 latency supporting the decision. Dense-only scores explain each model’s contribution; they should not determine the hybrid winner. The earlier Kiwi decision also prioritized fused retrieval quality over BM25-only improvement.

The following choices settle the consequential boundaries before turning this into a task specification.

I recommend keeping **five models in the actual benchmark, selected from a broader candidate list**. Your other decisions are settled: whitespace BM25, isolated and integrated comparisons, fixed weights followed by tuning, and a report without changing application defaults.

The local machine has an **RTX 3080 with 10 GiB VRAM**. That makes recent models around 0.3–1B parameters the most practical candidates. A 4B model is borderline at full precision; 8B models exceed this GPU’s capacity before accounting for inference overhead.

These estimates cannot guarantee that a model fits with the repository’s current batch size of 32. The benchmark should record actual peak VRAM separately for corpus indexing and single-query retrieval.

For reliability, I would distinguish **credible candidates from proven winners**. Official weights, model cards, papers, reproducible inference instructions and multilingual retrieval evaluations justify inclusion. They do not establish superiority on Korean RFP questions. In particular, an aggregate MTEB score combines multiple tasks and languages; our Kiwi-hybrid dev results must decide the winner.

There are several relevant implementation differences:

- Jina v5 small uses a retrieval adapter and is licensed CC BY-NC 4.0; commercial use requires separate terms. It remains a useful research comparison, but that restriction affects a deployment recommendation. [Official model card](https://huggingface.co/jinaai/jina-embeddings-v5-text-small).
- Perplexity’s native INT8 **output embeddings** do not mean its model weights consume INT8-sized VRAM. Its outputs require the documented cosine-similarity handling. [Official model card](https://huggingface.co/perplexity-ai/pplx-embed-v1-0.6b).
- EmbeddingGemma does not support FP16 activations. The repository’s blanket `.half()` behavior must not be applied to it; use its supported BF16 or FP32 path. [Official model card](https://huggingface.co/google/embeddinggemma-300m).
- Newness alone is insufficient. NVIDIA’s Nemotron 3.5 card states a release date of October 20, 2026—later than this session’s October 18 date—and says its text embedding space is shared with Nemotron 3. I would not count it as a separately verified, currently released text challenger. [Official model card](https://huggingface.co/nvidia/Nemotron-3.5-Embed-1B-BF16).

My preferred shortlist emphasizes four recent, differently trained challengers around the existing KURE baseline. Keep larger models in the candidate report, but do not silently introduce quantization or CPU offloading to fit them: either would change the performance comparison. The remaining decisions are the five-model lineup and whether this GPU is the intended benchmark machine.
