## Problem

improve() resumes a loop by reusing any run named {loop_id}-r{n} that has a manifest.json. It never checks that the run was created by this loop under the pinned plan, config and criteria. The invariant is that every round the loop reuses, validates, uses for open_bundles or counts in report.json must have been generated by this loop_id, at round n, from the plan, plan hash and start record pinned in start.json. A run that only shares the name, such as a standalone generate('A', ..., 'l1-r1') from plan p1, is adopted: it is validated against its own p1 and reported as a round of p3.

Trigger: repeat, rounds 1, 2.

- [P1] [P1] golden_pipeline/improvement.py:165 — A new loop can silently adopt a run from another plan

## Failed fixes

- Round 1 fix (01212b1): _pin writes start.json (config, plan_id, plan_sha256, thresholds) on first call and on later calls compares the current arguments with it. That binds the arguments to the record, but the reuse decision in _round (improvement.py:165, `if not (run_dir / 'manifest.json').exists()`) and the walk in _rounds (improvement.py:269-274) still decide ownership by name only. On the first call start.json is created from whatever arguments were passed, so there is nothing to compare against and any pre-existing {loop_id}-r1 is silently adopted (round 2 reproduction). The regression test (tests/golden/test_improvement.py:206-228) only covers changing arguments of an already recorded loop.
- Round 1's reviewer had asked to 'pin and verify the plan identity and hash before reusing rounds'. The fix verified the plan identity of the call, not of the reused rounds, so the same finding came back through a different entry path.

## Claims

- C1 (source; S1): Reusing a stored result under a caller-chosen key with different request parameters should be an error, not a replay.
- C2 (source; S2): Treating output existence as completion is a default that the tool itself says to override when existence is not sufficient.
- C3 (source; S3): _round and _rounds decide round ownership from the run name and manifest.json existence alone.
- C4 (interpretation; S3, S5): The round 1 fix bound call arguments to start.json but never bound reused runs to start.json, and start.json is created from the current call when absent, so pre-existing runs are adopted unchecked; the test only covered argument changes.
- C5 (interpretation; S1, S3, S4): Checking each reused manifest's policy.loop_id, policy.round, plan_id, plan_sha256 and a new policy.start_sha256 against the pin, in both _round and _rounds, closes both reproductions and a later foreign round.

## Core theory

When a stored result is looked up by a caller-chosen key and replayed, the key alone is not proof that the stored result answers the current request. The stored record must keep the original request, and a reuse whose request differs is an error, not a replay. Stripe made this change in 2015-09-03 for idempotency keys reused with different parameters. Systems that treat 'output exists' as 'task done' (Luigi's default Task.complete) inherit the opposite behaviour and must override completeness with custom logic when existence is not enough.

## Applicability

{loop_id}-r{n} is a caller-chosen key, and the run directory is the cached result that _round replays (golden_pipeline/improvement.py:161-178). generation.generate is a public entry point that accepts any run_id (generation.py:33), so a run with that name can exist without the loop having made it. The run manifest already stores the original request (generation.plan_id, plan_sha256, policy with loop_id and round; generation.py:70-80), so the comparison costs no new storage beyond adding the start.json hash to policy. The check belongs in _round (skip-generation branch) and _rounds (used by open_bundles at line 141 and _report at line 246); putting it in only one of them leaves the other reader adopting foreign runs.

## Hypothesis

Round ownership is inferred from the run name and the presence of a file. The pin covers the loop's inputs, not the provenance of the runs it reuses. The fix is one ownership check that every reused round passes through. A run belongs to round n of this loop only when its manifest.generation.policy has loop_id == loop_id and round == n, its generation.plan_id and plan_sha256 equal the pinned values, and policy.start_sha256 (new; _revision adds the sha256 of start.json) equals the sha256 of the current start.json. _round calls the check whenever it skips generation because the manifest exists. _rounds calls it for every directory it yields, so open_bundles and _report never read a foreign run. A standalone run has policy None and is refused.

## Counterevidence

- Luigi treats output existence as completion by design, so name-based reuse is a known, accepted convention in some pipeline tools. But Luigi documents complete() as overridable, and here the replayed run decides validation and report counts, so the convention does not fit.
- If start.json, config, plan and thresholds are byte-identical and loop_id matches, a run made by an earlier, deleted loop record would pass the check. That is arguably the same loop, so adopting it is acceptable rather than a hole.

## Alternatives

- Refuse at start only (when start.json does not exist yet, refuse if any {loop_id}-r* run or catalog entry exists). This closes the round 2 reproduction but misses a foreign run created at r{k+1} between an interruption and a resume. The manifest check covers that case and makes this one unnecessary.
- Give run ids a loop nonce (e.g. a uuid stored in start.json) so collisions cannot happen. This changes run ids that tests and reports rely on ('l1-r1'), and resume still has to verify ownership, so it adds work without removing the check.
- Compare only plan_id and plan_sha256 of reused manifests. This misses runs of another loop or of no loop that used the same plan, and config/threshold differences when the loop record was recreated. loop_id, round and start_sha256 are just as cheap to compare.

## Result

Observed, not verified: this is still a draft. The fix landed in the round-2 commit that carries this page ("golden_pipeline 자기 개선 리뷰 2 수정: ..."), on top of 8363fa8. Before the fix, the reproduction (plan p1, standalone `generate('A', 'numeric', 'p1', 'l1-r1', ...)`, then `improve('numeric', 'p3', 'l1', max_rounds=1)`) gave a report with plan_id p3 and rounds ['l1-r1'], while l1-r1/validation.json had plan_id p1. The fix follows the hypothesis: `_generated(topic, loop_id, n)` compares the manifest's policy.loop_id, policy.round, policy.start_sha256, generation.plan_id and plan_sha256 with the loop and start.json. `_round` calls it before skipping generation, and `_rounds` calls it for every directory it yields, so `open_bundles` and `_report` go through it as well. `_revision` adds start_sha256 to the policy. Tests: `tests/golden/test_improvement.py::test_a_loop_refuses_a_run_under_its_name_that_it_did_not_make` with three cases: a standalone run of another plan (all five keys differ), a standalone l1-r3 created after an interruption (loop_id, round, start_sha256), and start.json recreated with a different max_calls (start_sha256). Each raises ValueError naming the run, makes no generator call and writes no report.json. All three fail on 01212b1's improvement.py and pass on the fix. The unchanged resume test (`test_resume_continues_after_the_last_completed_round_without_duplicate_ids`) passes on both, so rounds the loop owns are still reused. As the Counterevidence section predicted, a start.json recreated with identical bytes is accepted as the same loop. The manifest-less crash window from Unresolved limits was not addressed.

## Unresolved limits

Not run here (no shell). One crash window stays outside this check: write_run creates the run directory before it writes manifest.json (storage.py:51-57). A crash in between leaves a directory with no manifest, and on resume _round tries to generate and new_run_dir raises FileExistsError. That is a separate issue from adoption. Whether start_sha256 should hash the raw start.json bytes or a canonical JSON dump is a detail for the fix; raw bytes are simplest because _pin writes the file once.
