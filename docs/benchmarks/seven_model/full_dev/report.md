# 일곱 임베딩 모델 재측정 (전체 dev, 과거 기록)

이 문서는 문맥 앵커 재측정 전에 잰 과거 기록입니다. 측정할 때 코드와 결과 파일의 해시(파일 내용을 확인하는 값)를 남기지 않았기 때문에, 지금의 [측정 규약](../protocol.md)으로 검증됐다고 말할 수 없습니다. 아래 추천은 당시의 결론으로만 읽어 주세요. 같은 방법으로 다시 잰 최신 결과는 [문맥 앵커 재측정](../anchor/report.md)에 있습니다. 수치는 당시 로컬 기록을 옮긴 것이며, 이번에 다시 측정하지 않았습니다.

- 당시에는 Nemotron을 추천했습니다. Kiwi 하이브리드의 검증 95문항에서 Recall@10이 78.42%로 가장 높았기 때문입니다. KURE의 0.6 고정(74.74%)보다 3.68%p, KURE가 튜닝으로 고른 0.8(71.58%)보다 6.84%p 높았습니다.
- 다만 Nemotron은 GPU 메모리와 색인 공간을 더 쓰고, 답변 모델에 넘어간 근거(Coverage)는 KURE보다 적었습니다. 작은 dev 표본에서 낸 추천이라, 일반적으로 더 낫다거나 도입해도 된다는 뜻은 아닙니다.
- 서비스의 모델, 가중치, 색인, Kiwi 규칙과 사전은 바꾸지 않았습니다.

RTX 3080 10 GiB에서 일곱 모델을 차례로 다시 실행해 잰 값이며, [첫 측정](../historical/report.md)의 점수를 다시 계산한 것이 아닙니다. 모델 발행자의 공개 점수와도 섞지 않았습니다. 용어는 [문맥 앵커 재측정의 용어 표](../anchor/report.md#용어)와 같습니다.

이 문서에는 집계 수치와 측정 조건만 적었습니다. 실제 질문·정답·근거, 문항별 결과, 분할 목록은 공유하지 않는 로컬 폴더 `artifacts/seven_model_full_dev/record/`에만 있습니다.

## 첫 측정에서 고친 것

- **빠진 질문 24개를 다시 넣었습니다.** 첫 측정은 dev 408문항 중 384문항과 YAML 1문항만 검색했습니다. 평가 입력을 고르는 함수(`check_eval_items`)가, 답변 채점에 쓰는 핵심 사실(key_facts)이 없는 여러 근거 질문 24개를 뺐기 때문입니다. 검색 평가에서는 이 조건을 없애고 408문항을 모두 검색했습니다. YAML 문항은 원본은 남기되 골든 비교에서는 뺐습니다.
- **근거 데이터를 원본 그대로 되살렸습니다.** v11 데이터 폴더 연결이 깨져 있었지만 다른 데이터로 바꾸지 않았습니다. 원래 생성 계획 11개의 묶음 번호와 근거 참조 716개가 모두 정확히 맞는 원본을 찾아 복구했고, 716개 모두 원본 골든 문맥의 근거와 하나씩 대응했습니다. 첫 측정에 있던 근거 653개도 그대로였습니다.
- **단어 검색이 제대로 돌았는지 확인했습니다.** 저장된 Kiwi 토큰이 18,989개 청크를 새로 나눈 결과와 같았고, 질문 408개도 한꺼번에 나눌 때와 하나씩 나눌 때가 같았습니다. 세 사례를 골라 BM25 점수 계산과 순위를 손으로 다시 따라가 봤고, 계산 오류는 없었습니다. 첫 측정의 Recall과 MRR 값 6,744개도 따로 다시 계산한 값과 같았습니다. 점수가 같은 오답 후보 두 개의 순서가 달랐던 경우가 있었지만, 정답 순위에는 영향이 없어 그대로 두었습니다.

모델 이름과 버전은 [models.json](../models.json), 모델별 설정과 라이선스는 [측정 규약](../protocol.md)에 있습니다.

잘못된 전제 주제는 이번 검증 분할에 청크 채점 문항이 없어 뺐습니다. Nemotron은 문항이 많은 두 주제에서 KURE보다 높지만, 표·비교·여러 근거 주제는 채점 문항이 너무 적습니다.

요구사항 번호가 든 검증 질문 42개 중 문서 채점이 되는 41개에서, 그 번호가 든 문서가 결과에 들어간 비율은 서비스 경로 100%, 실험 경로 0%였습니다. 실험 경로는 번호 우선 배치를 껐기 때문입니다. 이 질문들은 청크 채점이 되는 것이 없어서 청크 단위 값은 내지 않았습니다. 이 포함 비율은 순위와 상관없는 별도 지표이며, Recall과 다릅니다.

## 응답 시간과 자원

Windows 10.0.26200, RTX 3080 10 GiB, 메모리 약 63.82 GiB인 PC에서 모델마다 새 프로세스로 차례로 실행했습니다. Python 3.10.11, PyTorch 2.11.0+cu128, Transformers 5.19.0, Sentence Transformers 6.1.0, Kiwi 0.24.0을 썼고, 전체 버전은 [runtime-freeze.txt](runtime-freeze.txt)에 있습니다. 다른 프로그램은 끄지 않았습니다.

질문은 하나씩 넣고, 질문 임베딩은 캐시하지 않았습니다. 설정마다 처음 3번은 예열로 빼고, 순서를 섞어 세 번 반복했습니다. 질문을 넣을 때부터 답변 모델에 넘길 근거가 나올 때까지 쟀고, 모델 불러오기·색인 만들기·지표 계산 시간은 뺐습니다. 설정마다 1,224번, 검증 분할은 615번(한 번에 205번) 잰 값입니다. 세 번 반복한 결과의 후보·점수·근거는 모두 같았습니다.

## 당시 추천

검색 정확도(검증 분할의 청크 R@10)를 가장 중요하게 보면 Nemotron이 0.6 고정과 고른 가중치 모두 1위라 Nemotron을 추천했습니다. 고른 가중치의 R@20도 KURE 91.58%보다 조금 높은 92.11%였습니다.

하지만 다른 지표에서는 KURE가 나은 곳도 있었습니다.

| 항목 | KURE | Nemotron |
| --- | ---: | ---: |
| dev 전체, 고른 가중치 R@20 | 94.33% | 92.78% |
| 검증 Coverage | 69.47% | 68.42% |
| 근거 여러 개, 모두 담은 문항 | 7 / 13 | 6 / 13 |
| p90 응답 시간 | 약 172ms | 약 210ms |
| GPU 메모리 | 약 1.25 GiB | 약 2.64 GiB |
| 전체 색인 크기 | 약 138 MiB | 약 259 MiB |

메모리, 응답 시간, 근거를 빠짐없이 담는 것이 더 중요하다면 KURE도 합리적인 선택입니다. 어느 한 모델이 확실히 낫다고 보지 않습니다.

라이선스도 확인해야 합니다. Jina는 상업적 이용을 막는 CC BY-NC 4.0이고, upskyy는 라이선스가 정해져 있지 않습니다. Nemotron은 OpenMDW-1.1입니다. 이 보고서가 사용 허가를 새로 주지는 않습니다.

일곱 모델 모두 같은 코드(커밋 `423d453`)로 쟀습니다. 측정 중 네트워크 연결 시도는 없었고, API는 하나도 부르지 않았습니다. 사용 기록, 서비스 색인, 기본 설정은 그대로이며 test 분할은 실행하지 않았습니다. 영향받은 테스트 114개가 통과했고 ruff 검사도 통과했습니다.
