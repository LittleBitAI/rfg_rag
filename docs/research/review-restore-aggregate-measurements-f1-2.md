# 리뷰 조사 · F1, 2회차

PR #67 리뷰 3회차의 수정 전에 2026-10-19에 쓴 조사 초안입니다. 검증된 사실이나 공용 규칙이 아니며, 리뷰는 이 문서를 수정과 함께 읽습니다.

## 문제

F1의 불변 조건은 실제 데이터셋 레코드와 발췌를 공개 Git에 커밋하거나 올리지 않고, 레코드가 없는 집계만 공개하는 것입니다. 첫 수정은 지금 보고서의 내용을 정리했고, 다음 수정은 작업 브랜치 이력을 바꿨지만, 이미 올라간 내용의 원격 접근을 막았다는 것까지는 증명하지 못했습니다. 그 상태에서 조사 문서가 과거 내용을 찾는 위치와 명령을 공개했습니다. 이번 조사는 원문과 그 식별자를 다시 적지 않습니다. [C1, C3, C4, C7]

발생: 반복, 2·3회차.

- [P0] docs/research/review-restore-aggregate-measurements-f1-1.md — 아직 조회 가능한 비공개 레코드의 위치를 다시 공개함. 상세 조회 위치는 비공개 로컬 사고 목록에만 보관한다.

## 실패한 수정

- 1회차 뒤 수정은 두 보고서의 실제 사례를 집계와 일반 설명으로 바꿨습니다. 지금 파일에서 이 변경을 확인할 수 있습니다. 그러나 이전 조사의 관측 기록에 따르면, 당시 오염된 커밋은 작업 브랜치의 조상이자 PR 커밋으로 남았습니다. 파일 삭제를 더하는 커밋은 과거 내용을 지우지 못했습니다. [C3, C4]
- 2회차 뒤 수정은 정리한 파일을 지키면서 작업 이력을 바꿨습니다. 작업 조상에서 오염된 커밋을 빼는 조치였지만, 조사 문서 스스로 공유 base, 다른 참조, GitHub 캐시, 과거 PR 참조가 지워졌다는 것을 증명하지 않았고 Support 삭제 요청도 하지 않았다고 적습니다. 그래서 원격 삭제를 끝내는 수정이 아니었습니다. [C4, C5, C7]
- 같은 수정에서 조사 문서에 과거 커밋 식별자, 민감한 내용의 정확한 위치, 조회 명령을 남겼습니다. 원문을 다시 인용하지 않았다는 점만으로는 이 안내가 드러내는 효과를 없앨 수 없습니다. 이전 조사의 맥락 손실 가설도 실제 파일·이력 관측과 별개로 확인되지 않은 설명으로 남아 있어, F1 해결의 근거가 되지 못했습니다. [C4, C7]

## 주장

- C1 (출처; S1): 저장소는 실제 레코드와 발췌의 커밋·업로드를 금지하고, 그 내용이 없는 집계의 공개는 허용합니다.
- C2 (출처; S2): 벤치마크 약속은 문항별 감사, 순위, 점수, split ID는 로컬에 두고 집계 파일은 Git에 두도록 나눕니다.
- C3 (해석; S3, S4): 지금 두 보고서의 감사 문단은 개별 사례 대신 집계와 일반 설명으로 정리되어 있습니다. 이것은 지금 내용 정리의 증거입니다.
- C4 (해석; S5): 이전 조사는 첫 내용 정리 뒤에도 오염된 조상이 남았다고 적고, 후속 이력 교체가 원격 삭제를 증명하지 않는다고 한정합니다. 같은 문서에 과거 내용을 찾는 식별자와 명령이 남아 있습니다.
- C5 (출처; S6): GitHub는 이력을 바꾼 뒤에도 외부 사본과 PR·캐시 접근이 남을 수 있다고 설명합니다. 서버 삭제에는 선행 조건과 Support의 민감성 판단이 있으며, 지원은 보장되지 않습니다.
- C6 (해석; S7): Git의 로컬 GC는 여러 참조가 가리키는 객체를 보존하므로, 지금 브랜치 조상에서 빠졌다는 사실만으로 객체가 지워졌다고 볼 수 없습니다.
- C7 (해석; S5, S6, S7): 이번 반복의 직접적인 설명은 검증 범위가 F1의 공개 경계와 맞지 않았다는 것입니다. 내용 정리와 조상 교체는 필요했지만, 공개 조회 안내와 원격 접근 가능성은 따로 처리할 일로 남았습니다.
- C8 (해석; S1, S2, S5, S6): 알맞은 다음 조치는 공개 문서의 조회 안내 지우기, 관리할 수 있는 오염 참조 조사와 정리, 조건에 맞는 원격 삭제 처리, 처리 뒤 접근 확인입니다. 자세한 증거는 비공개로 두며, 과거 업로드를 취소했다거나 기존 사본을 모두 지웠다고 보장하면 안 됩니다.

## 핵심 원리

Git에서 닿을 수 있는지를 바꾸는 일과 객체를 지우는 일은 별개입니다. Git은 브랜치 밖의 참조와 reflog 등이 가리키는 객체도 보존합니다. GitHub도 이력을 다시 쓴 뒤의 접근 가능성과 서버 쪽 삭제를 구별하며, Support 지원에는 민감성 판단과 삭제 선행 조건이 있습니다. [C5, C6]

## 적용

지금 두 벤치마크 보고서의 감사 문단은 집계와 일반 설명으로 정리되어 있습니다. 다음 편집의 직접 대상은 이전 조사 문서에 남은 오염 이력 식별자, 정확한 위치, 조회 명령입니다. 같은 안내가 공개 색인이나 PR 설명에 복사되었는지도 확인해야 합니다. 자세한 사고 목록은 무시되는 로컬 artifacts에 두고, 공개 문서에는 범위, 처리 상태, 검증 한계만 남기는 것이 알맞습니다. 따로 관리할 수 있는 오염 참조와 fork를 조사하고, 필요한 원격 삭제는 GitHub의 조건부 Support 절차로 처리해야 합니다. Support 수락이나 삭제 완료를 문서 편집으로 대신할 수는 없습니다. [C1, C2, C3, C5, C7, C8]

## 가설

반복 실패의 원인은 완료 기준을 지금 파일, 작업 브랜치 조상, 원격 공개 접근 순으로 좁혀 가며 검증한 데 있습니다. 마지막 수정은 브랜치 정리는 증명했지만 원격 잔존은 풀지 않은 채 남겼고, 공개 조사 문서에는 남은 내용을 찾는 안내를 더했습니다. 다음 수정은 공개 안내 지우기와 원격 잔존 처리·확인을 함께 다뤄야 합니다. 실제로 무엇이 남게 하는지, 즉 PR 내부 참조인지 캐시인지 다른 참조인지는 아직 짚을 수 없습니다. [C4, C5, C6, C7]

## 반대 근거

- 지금 보고서의 그 문단에서는 실제 사례 대신 집계와 일반 해석을 확인했습니다. 첫 내용 정리 자체가 실패했다고 볼 근거는 없습니다. [C3]
- 이전 조사는 원격 삭제를 끝냈다고 적지 않았고 한계를 기록했습니다. 문제는 한계를 숨긴 것이 아니라, 그 한계가 남은 채로 F1을 해결로 다룬 것입니다. [C4, C7]
- GitHub 문서는 남을 수 있는 경로를 설명할 뿐, 이 저장소의 실제 잔존 경로를 짚지 않습니다. 이번 세션은 과거 원격 응답을 재현하지 않았습니다. [C5, C7]
- 저장소의 비공개 약속과 GitHub Support의 민감 데이터 판정이 같은 기준이라고 단정할 수 없습니다. Support가 지원을 거절할 가능성도 남습니다. [C1, C5, C8]

## 다른 방법

- 보고서나 조사 문서의 지금 내용만 다시 지우기. 공개 안내를 줄이는 데는 필요하지만, 원격 과거 객체의 접근을 막았다는 증명이 되지 못하므로 이것만으로는 모자랍니다. [C5, C7]
- 작업 브랜치를 다시 squash하거나 force-push하기. 오염된 조상이 실제로 남아 있다면 필요하지만, 이미 조상을 바꾼 상태에서 되풀이해도 원격 잔존을 풀었다는 증거는 늘지 않습니다. 먼저 남은 참조와 접근 경로를 확인해야 합니다. [C4, C5, C7]
- 로컬 garbage collection을 돌리거나 자동 삭제를 기다리기. 로컬 저장소 정리는 GitHub 서버 처리의 증거가 아니며, 객체 보존은 참조와 설정에도 달려 있습니다. [C5, C6]
- 자격 증명을 바꿔서 해결하기. 이번 대상은 데이터셋 내용이므로, 바꿀 수 있는 비밀 키처럼 무효로 만들 수 없습니다. 다만 이 판단이 Support의 지원 수락을 보장하지는 않습니다. [C1, C5, C8]
- 이전 조사의 호스트 맥락 손실 가설부터 조사하기. 그 문서 스스로 확인되지 않았다고 한정하며, 이미 기록된 파일·이력 노출을 풀지 못합니다. 지금 F1에서는 공개 경계와 원격 삭제를 먼저 다루는 것이 맞습니다. [C4, C7]

## 실험

다음 수정 세션에서 다음을 나눠 확인합니다. ① 비공개 로컬 사고 목록으로 알려진 원문과 오염 이력 식별자를 대조하되, 결과에는 일치 건수와 처리 상태만 남깁니다. 지금 추적 파일, 공개 색인, 공개 설명에 원문과 조회 안내가 없는지, 허용된 집계가 남아 있는지 확인합니다. ② 관리할 수 있는 브랜치, 태그, PR 이력, fork의 오염 참조를 조사해 정리 범위를 정합니다. ③ 필요한 Support 처리에는 자세한 식별자를 비공개로 주고, 처리가 끝났는지와 예외를 적습니다. ④ 처리 뒤 기존 접근 경로를 통제된 환경에서 다시 확인합니다. 오류 응답은 정상 공개 대조 요청과 비교해 인증 실패나 요청 제한(rate limit)과 구별합니다. 브랜치에서 빠졌는데 과거 내용이 계속 돌아오면 가설이 뒷받침됩니다. 공개 접근 불가와 서버 처리 증거를 함께 얻으면, 관리할 수 있는 원격 범위가 복구되었다는 것을 뒷받침합니다. 이 확인은 아직 돌리지 않았습니다. [C5, C7, C8]

## 결과

구현 세션에서 관측했으며, 따로 검증하기 전의 초안입니다. 수정 커밋은 이 문서와 공개 안내 지우기, 검토 설명 수정을 함께 담은 `docs: remove disclosure guides and correct review evidence`입니다. 비공개 로컬 사고 목록 대조에서, 지적된 이전 조사 문서에 조회 식별자 11회, 따로 공개된 PR 본문에 15회를 확인했습니다. 공개 색인과 PR 댓글·리뷰에서 더 맞는 것은 없었습니다. 지금 문서의 조회 식별자, 과거 위치, 명령을 지우고, PR 본문도 처리 상태와 건수만 남기도록 정리합니다. 공개 브랜치 9개에는 조사한 오염 커밋이 조상으로 없었고, 공개 태그와 fork는 각각 0개였습니다. 인증 없는 HTTP 대조에서 정상 공개 파일은 200이었고, 과거 객체 두 건도 모두 200으로 실제 감사 문구 4개와 2개를 돌려줬습니다. 남은 요청 한도도 확인했으므로, 인증 실패나 요청 제한 때문에 접근 결과를 잘못 판단한 것은 아니었습니다. 이 관측은 브랜치 정리를 원격 접근 차단과 같은 것으로 본 가설을 반박하고 원격 잔존이 있다는 것을 뒷받침하지만, 남은 원인이 내부 PR 참조인지 캐시인지는 짚지 못합니다. 자세한 식별자와 응답 원문은 공개하지 않습니다. Support 처리는 접수하지도 끝내지도 않았고, 원격 접근 차단은 풀리지 않았습니다. F1을 해결로 분류하지 않습니다. 처음 수정에서는 제품·테스트 코드를 바꾸거나 pytest를 돌리지 않았고, 이어진 집중 실행은 아래에 따로 적습니다. 서버가 맡는 전체 검사는 아직 기다리는 중입니다. [C4, C5, C6, C7, C8]

오프라인 점검에서 `.venv/Scripts/ruff check .`는 `All checks passed!`, `git diff --no-index CLAUDE.md AGENTS.md`와 `git diff --check`는 exit 0이었습니다. 비공개 목록을 쓴 Python 대조로, 지금 추적 파일과 공개 색인에 알려진 조회 식별자와 실제 감사 문구가 각각 0개임을 확인했습니다. 앞서 정리한 작업 파일 61개 가운데 조사 문서 두 개, 검토 보고서, 문서 색인 두 파일을 뺀 56개는 바이트가 같았고, 집계 파일은 모두 남겼습니다. 공개 보고서와 protocol의 상대 링크 26개는 추적 파일로 이어졌습니다. 제품·테스트·설정·의존성 변경은 0개이며, 바뀐 다섯 파일은 BOM 없는 UTF-8입니다. F2의 diff 접기 주장은 `git check-attr linguist-generated`로 네 경로가 모두 unspecified이고 비공개 provenance 파일이 추적되지 않는 것으로 재현했으며, 같은 주장을 담은 다른 문서는 0개였습니다. 보고서는 실제 속성과 공개 검토 범위에 맞게 고쳤습니다. 공개 안내가 이전 작업 커밋에도 있으므로 이 작업 이력만 다시 바꾸지만, 이를 원격 삭제 증거로 다루지 않습니다. 자세한 사고, 참조, 지원 요청 초안은 무시되는 로컬에만 둡니다. Support에 제출하지 않았으며, F1 전체 해결은 미룹니다.

### 이어진 테스트 정리와 집중 재실행

이어진 요청에 따라 실제 diff와 관련 테스트를 다시 감사했습니다. `git diff --name-status d7d1682 HEAD -- rag frontend tests config.yaml 'requirements*' ':(glob)golden_pipeline/**/*.py'`는 출력 없이 exit 0으로 끝나, 제품·테스트·설정·의존성 변경이 없음을 확인했습니다. 그래도 비공개 로컬 입력과 산출물 경계에 관련된 다음 세 파일을 읽고, 지금 동작을 지키는지 확인했습니다.

- `tests/test_local_inputs.py`: 비공개 입력을 손실 없이 복원하고, 덮어쓰기를 막으며, 독립 소비자와 CLI 경로를 지킵니다.
- `tests/test_notebook_settings.py`: 저장된 실행 결과가 없는 상태와 OCR·검색·생성 설정 전달을 지킵니다.
- `tests/test_retrieval_benchmark_artifacts.py`: 따로 지은 합성 자료의 봉인, 고정 가중치, 순위, 문맥, 시간 표본, 경로 일관성을 지킵니다. 실제 레코드를 공개하지 않더라도 로컬 파이프라인의 이 동작은 남아 있습니다.

세 파일의 테스트 함수 16개에 만료된 skip·xfail은 0개였고, 지운 경로·형식·옵션을 검사하거나 더 강한 검사로 대체된 중간 테스트나 겹치는 관측은 없었습니다. 테스트는 더하거나 지우거나 합치지 않았습니다. 정리 뒤 `.venv/Scripts/python -m pytest -q tests/test_local_inputs.py tests/test_notebook_settings.py tests/test_retrieval_benchmark_artifacts.py`는 `46 passed, 4 warnings in 68.17s (0:01:08)`로 끝났습니다. 경고 네 개는 기존 RAGAS 사용 중단 경고입니다. `.venv/Scripts/ruff check .`는 `All checks passed!`, 규칙 파일 대조도 exit 0이었습니다. 감사 기록 커밋은 이 문서와 그 색인을 담은 `docs: record test cleanup audit for review repairs`입니다. 이 집중 실행은 원격 삭제나 전체 검사 통과의 증거가 아니며, F1은 여전히 풀리지 않았습니다.
