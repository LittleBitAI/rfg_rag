# Kiwi BM25 tokenizer review: five tokenizer variants measured on free dev retrieval eval, kiwipiepy pinned (PR #64 merged)

The user asked whether the Kiwi morphological analyzer behind BM25 is advanced enough. The review found a sound but basic setup with clear gaps, and no measurement that isolates tokenizer quality. The user chose a review plus measured fixes: five tokenizer variants scored alone, then the winners combined, on the original question text at no API cost. A variant is adopted only if it passes the win rule, and kiwipiepy is pinned to 0.24.0. The work landed as PR #64, merged after review round 4 with 0 remaining P2 issues.

## Decisions

- Scope is a review plus measured fixes; tokenizer defaults stay unchanged unless a variant wins
- Measure on all labelled dev questions using the original question text, with no paid rewrites — It is free: rebuilding the index and the existing rerun_retrieval path need no API calls, while more stored rewrites need paid rewriting (rejected: Only the 30 dev questions with stored rewrites, or paying for more rewrites)
- Variants to test: keep joined compound nouns alongside the split parts; drop noise tokens (및, 하, other function-like MAG/VV); grow the user dictionary from the corpus and agency list; keep hyphenated identifiers whole (ISMS-P, GS인증); pin kiwipiepy to the measured version — Each variant targets a gap found in the tokenizer probe
- Win rule: fused chunk Recall@10 must improve and no metric may drop by more than 0.01
- Comparison method: score each change alone, then the winners combined
- For the quantity parser, only the version pin applies; its analysis stays untouched
- User dictionary source: the agency list in data/data_list.csv plus frequent RFP compound nouns mined from the active chunks
- Pin kiwipiepy to 0.24.0 — requirements.txt allowed kiwipiepy>=0.20, and Kiwi does not promise identical analyses across versions, so the team VM index could differ

## Facts

- KiwiTokenizer in rag/retrieval/indexing.py produces BM25 tokens for both chunks and queries (unverified)
- Before this work, the tokenizer used default Kiwi() and kept nouns, verb and adjective stems, foreign words, Hanja, numbers and general adverbs (unverified)
- It kept the negations 않 and 아니, added a Hangul reading for each Hanja token, and appended requirement codes such as sfr-001 as extra tokens (unverified)
- Before this work, the user dictionary had 7 words (지체상금, 부가가치세, 하자보수, 과업지시서, 제안요청서, 기술협상, 공동수급) and one alias (부가세 → 부가가치세); spaced-out forms of these words are joined before analysis (unverified)
- The requirement-code regex catches only 2–5 letters plus 2–4 digits, so ISMS-P was split into isms and p (unverified)
- Kiwi's built-in dictionary emits 전자정부 표준프레임워크 as one token that contains a space (unverified)
- Before this work, the last real change to the tokenizer logic was the PR #21 port of the search lead's feature/Retrieval work (unverified)
- BM25 uses k1=1.5 and b=0.75 and gets 40% of the fused score (dense_weight: 0.6) (unverified)
- Before this work, requirements.txt allowed kiwipiepy>=0.20; the local PC had 0.24.0 (unverified)
- The quantity parser runs its own separate default Kiwi() with no user words; in one review round it analysed 인 전체 사업 as three general nouns, which broke project recognition (unverified)
- Baseline chunk-level recall on the 15 fully chunk-labelled questions of the 30-question dev sample: BM25-only R@5/10/20 = 0.567/0.667/0.733; dense-only 0.700/0.867/0.933; fused 0.667/0.800/0.867 (unverified)
- Document-level recall is 1.0 for all components because agency routing does that work (unverified)
- The labelled evaluation set has 385 items, 376 of them answerable with labelled evidence; each carries document and chunk labels produced by step 03 (unverified)
- The rules forbid running the test split during retrieval-metrics work (unverified)

## Preferences

- Defaults stay unchanged unless a measured variant wins under the win rule
- Measurement should cost nothing in API calls
