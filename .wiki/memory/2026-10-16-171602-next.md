# RAG evaluation redesign: golden evidence-to-chunk mapping audit first, then IR retrieval metrics and fewer RAGAS calls

The user asked to replace the LLM-based RAGAS retrieval metrics (context_precision, context_recall) with deterministic IR metrics (Recall@k, MRR@k, Evidence Coverage) and to cut answer_relevancy. They also asked that the golden evidence be verified against the live retriever chunks before anything else. Analysis found that golden chunk IDs match none of the live index chunk IDs. Document IDs can be bridged through the raw-file SHA-256, and chunk labels are only partly recoverable by text matching. The user set the split, labelling rule, ranking input, a component-split 'semantic accuracy' check and a 30-question paid sample. Two specs were written (mapping audit, then evaluation), and PR #54 and PR #57 were later merged.

## Decisions

- Two specs in sequence: the evidence-mapping audit first, then the evaluation spec (IR metrics, RAGAS cuts, 30-question paid sample, README and notebook). The second spec branches from dev after the audit PR merges. — The metric levels in the evaluation spec depend on the mapping rates the audit produces.
- Chunk labels come from exact normalized text containment within the same document only. Evidence that is unmatched or appears in more than one chunk gets no label, and every miss is recorded with its reason. — The user required that no correct-answer chunk be fixed by a semantic-similarity threshold alone and that no label be invented when mapping is uncertain. (rejected: Semantic-similarity threshold matching)
- Document labels link each golden evidence entry to a live document by matching `doc_sha` to the SHA-256 of the raw file. — Golden chunk IDs do not exist in the live index, but `doc_sha` matches raw files and the live chunks record the filename as `source`.
- Ranking input: add a read-only ranked output next to `search()`, record chunk_id and rank in answers.jsonl, and reuse each item's stored query rewrite. — answers.jsonl has no chunk IDs or ranks and keeps only the chunks left after the token budget. Each rewrite is a paid API call. The retriever's search behavior must not change.
- 'Semantic accuracy' is covered by splitting retrieval results by which component found each labelled chunk: dense (KURE-v1), BM25 or exact requirement code. — The retriever mixes embedding-based search with other methods, and the user wants to confirm the embedding part actually works.
- The paid LLM sample is 30 dev questions, run only after an estimate is shown and the user approves.

## Facts

- Golden sets in the repo are `eval/golden/dev.jsonl` (408 questions, 30 documents) and `eval/golden/test.jsonl` (943 questions, 68 documents). These are assumed to be the golden_dev.jsonl and golden_test.jsonl the user named. (unverified)
- Golden item schema: `question`, `answer`, `primary_topic`, an `evidence` list (each entry has `doc_sha`, `chunk_id`, `element_id`, `record_id` with a character range, and `page`) and a `context` field holding the evidence text as `[E1]`, `[E2]` blocks. 84 of the 408 dev questions cite more than one chunk. (unverified)
- 0 of 716 dev evidence `chunk_id`s and 0 of 1,639 test ones appear in the active chunk file `artifacts/chunks/chunks_1d8e299209e8.jsonl`. Golden IDs are short hex IDs from the v11 package's `final_chunks.jsonl`, while the live index uses `<doc_id>::c00000` IDs. This contradicts the README's claim that v11 chunk IDs are kept. (unverified)
- 35 of 36 distinct dev `doc_sha` values match a file in `artifacts/raw` by SHA-256, so document-level Recall@k and MRR look feasible once the one unmatched document is excluded. (unverified)
- A rough text-match probe on the 573 dev `[E]` blocks (whitespace and `|` stripped, searched within the same document) gave: about 65% in exactly one chunk, about 8% ambiguous, about 12% not found, about 13% under 10 characters, about 3% with an unmapped document. Blocks were paired with entries by position (573 blocks for 716 entries), so this is not a final mapping rate. (unverified)
- answers.jsonl stores only `contexts` (chunk bodies) and `sources` (filenames): no chunk IDs, no ranks, and only post-token-budget chunks. The pre-budget ranked list is not recorded anywhere. (unverified)
- Search runs on an LLM-rewritten question, and each rewrite is a paid API call. (unverified)
- The retriever merges three candidate sources: dense (KURE-v1) top `candidate_k`, BM25 top `candidate_k`, and exact requirement-code matches placed first. (unverified)
- `answer_relevancy` is the only embedding-based metric today. It uses KURE on the evaluation side and measures whether the answer resembles the question, not whether dense search finds the right evidence. (unverified)
- Questions from `eval/eval_questions.yaml` have no golden evidence. They are reported as unlabeled and excluded from the IR metrics. (unverified)
- CLAUDE.md and AGENTS.md section 5 list the current evaluation metrics. (unverified)
- PR #54 was merged after review round 3 with 0 remaining P2 issues, and PR #57 after round 4 with 0 remaining P2 issues.

## Preferences

- Keep evaluation reliability while minimizing unnecessary LLM calls; do not just remove RAGAS or swap metrics.
- Keep document-level and chunk-level retrieval success strictly separate. Retrieving an unrelated chunk from the correct document is not an evidence hit.
- Evaluate the ranked search candidates (A) separately from the context actually passed to the LLM after the token budget (B). Record search settings, k and token budget with results.
- Do not change the existing Retriever's search behavior for the sake of evaluation.
- Do not create a correct-answer label when mapping is uncertain. Report mapping success rates, failure cases and the missing rate, and make mapping accuracy checkable by sampling.
- Separate single-evidence questions from multi-hop and comparison ones, and do not use MRR as a completeness measure for multi-evidence questions.
- Keep faithfulness and factual_correctness as distinct LLM metrics. Keep key_facts_in_answer and key_facts_in_context, noting that string matching is not semantic correctness. Lean toward dropping answer_relevancy from the default set.
- Use dev for retriever and hyperparameter experiments and error analysis. Reserve test for final pipeline scores used in the bootcamp final presentation.
- Never run paid LLM evaluation on the full dataset without explicit instruction.
- Unit tests for Recall@k, MRR@k and Evidence Coverage must not call paid APIs.
- Keep existing API usage tracking and result CSV saving, and keep old RAGAS results clearly separate from new IR results.
- Follow the existing code style and config structure, and reflect changes in the README and the related notebook (05_evaluation.ipynb).
- Every metric must be explainable in the bootcamp final presentation: what it means and how reliable it is.
