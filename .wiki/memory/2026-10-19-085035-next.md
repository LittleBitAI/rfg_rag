# Plan for offline dev-set retriever method and embedding-model benchmark, weighted toward Kiwi BM25 hybrid (7 models, RTX 3080)

The user asked how to structure two API-free dev-set experiments. The first compares retrieval methods: whitespace BM25, dense only, Kiwi BM25, Kiwi BM25 + embedding, and whitespace BM25 + embedding. The second compares embedding models, dense only and with Kiwi BM25, with p50/p90 latency, and its conclusion favors the Kiwi hybrid. They settled on a two-stage shared benchmark: methods with KURE-v1 fixed, then a 7-model lineup run sequentially on the local RTX 3080. The output is a report and recommendation. The session ended with PR #66 merged (round 7, 0 P2 items remaining).

## Decisions

- "Standard BM25" baseline uses whitespace tokens — BM25 needs a tokenizer definition, and the earlier Kiwi baseline already used morphological analysis, so it is not a non-Kiwi baseline
- Measure both isolated retrieval methods and the integrated (deployed) pipeline — Setting dense_weight to 0 or 1 does not isolate a method: exact requirement-code promotion and the quantity-filter path still run (rejected: isolated-only or pipeline-only comparison)
- Fusion weights: run fixed weights first, then tune
- Completion is a report and recommendation, without changing application defaults (rejected: changing defaults as part of the work)
- Embedding benchmark lineup: the recommended shortlist (KURE-v1 baseline plus four recent challengers), plus dragonkue/BGE-m3-ko and upskyy/bge-m3-korean, for seven models total — User asked for the two Korean BGE-M3 fine-tunes as additional Korean comparisons (rejected: larger 4B/8B models in the actual benchmark (kept only in the candidate report; no silent quantization or CPU offloading))
- Benchmark hardware is the current local RTX 3080 10 GiB, running models sequentially
- Run in two stages: retrieval methods with KURE-v1 fixed, then embedding models each alone and with the selected Kiwi tokenizer — Keeps tokenizer changes from being confused with embedding changes

## Facts

- Local GPU is an RTX 3080 with 10 GiB VRAM. 0.3–1B models are practical, 4B is borderline at full precision, and 8B exceeds capacity (unverified)
- The latest tokenizer experiment scored document retrieval on 376 answerable questions with golden evidence. Chunk retrieval used only 186 fully labelled questions; 190/376 (50.53%) were excluded, with comparison, multi-hop and table questions underrepresented (unverified)
- The earlier Kiwi tokenizer work compared Kiwi variants only, not the five methods. Its decision prioritized fused retrieval quality over BM25-only improvement (unverified)
- Setting dense_weight to 0 or 1 still applies exact requirement-code promotion, and quantity-filter questions can take another path (unverified)
- The context-budget token count currently uses the embedding model's tokenizer, so it must be frozen across models for comparisons (unverified)
- The repository's embedding batch size is currently 32, and the code applies a blanket .half() (unverified)
- EmbeddingGemma does not support FP16 activations; it needs BF16 or FP32 (unverified)
- Jina embeddings v5 text small is licensed CC BY-NC 4.0, so commercial use needs separate terms (unverified)
- pplx-embed's INT8 output embeddings do not reduce weight VRAM, and its outputs need the documented cosine-similarity handling (unverified)
- dragonkue/BGE-m3-ko uses CLS pooling. upskyy/bge-m3-korean uses mean pooling and reports only KorSTS/KorNLI similarity results, not retrieval results. Each is estimated at 2–4 GiB working VRAM at FP16 (unverified)

## Preferences

- No API calls in either experiment; use the dev set with original questions
- The embedding-model conclusion must lean toward Kiwi BM25 + embedding, because the hybrid is what will be used
- Report latency p50/p90 plus multiple quality metrics for embedding models
- Give as many candidate embedding models as possible, with required VRAM shown; prioritize recent models that are also credible

## Open

- Proposed but not explicitly confirmed: Kiwi-hybrid chunk Recall@10 as the primary model-selection criterion, supported by Recall@20, multi-evidence coverage, topic regressions and p90 latency
- Proposed metric set not explicitly confirmed: document/chunk Recall and MRR @5/10/20, evidence coverage and full coverage, p50/p90 latency (warm-up, batch 1, no query-embedding cache), index build time, index size, peak memory
- Recheck chunk-label mappings against the frozen corpus to improve coverage; the winner should be described as best on the eligible dev subset only
- Record actual peak VRAM separately for indexing and single-query retrieval
- The exact four challengers in the chosen shortlist were not named in the transcript
