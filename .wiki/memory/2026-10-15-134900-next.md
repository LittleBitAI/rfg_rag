# Golden dataset pipeline: six specs merged into dev, then a cleanup-first refactor spec and a paid gpt-5-mini pilot spec for method A

The user asked for six specs to build an independent golden-dataset generation pipeline under golden_pipeline/ that leaves existing pipelines untouched. All six were implemented and merged into dev (#22, #23, #24, #26, #28, #30). The user then asked how to check generation and requested an agent spec that tests method A's self-improvement loop with real paid calls, plus a refactor of needless tests and branchy code. Two specs were agreed: a free cleanup refactor first, then a paid pilot. PR #33 and #34 were merged afterwards; the transcript does not say which spec each one carries.

## Decisions

- dev is the base branch and PR target for all golden-data specs; branches named feature/golden-data-<piece>, cut from latest origin/dev after the previous PR merges — The team names branches feature/<topic> and opens PRs into dev; dev/feature/... names are impossible because a dev branch exists (rejected: main as base)
- Before running A/B/C, split the A check into two specs: refactor first, then a paid pilot of method A (rejected: a single combined spec)
- Pilot models: gpt-5-mini for both generator and validator, with generator reasoning effort low and validator reasoning effort high
- Pilot size: all five topics, 2 bundles each, 3 rounds, $3 total cap
- Pilot pass bar: the loop mechanics are shown with real files; improvement is reported but not required
- When refactoring, keep a test only if it guards behaviour that can break and no other test already guards it; keep a branch only if it protects data, money or the trust boundary; any behaviour change from simplifying falls to held, never to auto-accept — The user forbade tests-for-tests and branch-on-branch code accreted through repeated failing fixes

## Preferences

- Never change the existing team pipelines, rag/ or the existing ③ Validation; no rename, move, delete, formatting or incidental refactor of existing files
- Put all new code, tests, configs, docs, launchers and outputs only under golden_pipeline/
- Do not regenerate existing index, QA or evaluation artifacts
- Do not filter arbitrarily to match counts; reconcile the manifest with the actual inputs
- Hold conflicting numbers, missing evidence and data outside OCR scope out of auto-approval; never fix the source
- No tests for tests and no branch-of-branch code from repeated failed fixes; refactor any that exist
- Ask which model to use before paid calls; keep paid runs separate from implementation tests
- Never fill unobserved C costs or tokens with 0; do not assume the C web model matches the API model
- If progress needs a shared-file change, report the need and alternatives instead of editing
