# 현재 문제

현재 RAG 프로젝트에서는 RAGAS 기반 평가를 수행하고 있으나, 다음과 같은 문제가 있다.
- 데이터셋 전체를 반복 평가할 때 LLM API 호출이 많아 비용 부담이 크다.
- RAGAS 평가 지표가 5개로 구성되어 있어 평가 시간이 길다.
- 특히 Retrieval 단계는 본질적으로 정답 문서 및 근거 청크를 얼마나 정확하게 검색했는지 측정하는 것이므로, 반드시 LLM 기반 평가가 필요한지 의문이다.

현재 RAGAS 평가 구성은 다음과 같다.

| 영역 | RAGAS 지표 | 자체 지표 |
|---|---|---|
| Retrieval | context_precision, context_recall | key_facts_in_context |
| Generation | answer_relevancy | key_facts_in_answer |
| Grounding | faithfulness | - |
| End-to-End | factual_correctness | latency, tokens, cost |

**목표는 단순히 지표를 줄이는 것이 아니라, 평가의 신뢰성을 유지하거나 개선하면서 불필요한 LLM 호출을 최소화하는 것이다.**

# 개선 방향

## Retrieval 평가를 IR 기반 지표로 전환

현재 RAGAS 기반 `context_precision`, `context_recall`을 다음과 같은 전통적인 Information Retrieval 지표로 대체하는 방향을 검토한다.

- **Recall@k:** 정답 문서 또는 정답 청크를 얼마나 검색했는가?
- **MRR@k:** 첫 번째 정답 문서 또는 청크가 얼마나 상위 순위에 등장하는가?
- **Evidence Coverage:** 정답을 구성하는 핵심 근거들이 실제 검색 결과에 얼마나 포함되어 있는가?

가능하면 이 평가들은 LLM API 호출 없이 결정적으로 계산하도록 구현한다.

단, Recall@k와 MRR@k는 정답 문서나 청크에 대한 신뢰할 수 있는 relevance label이 있어야 계산할 수 있다. 단순히 정답 문서 ID가 존재한다고 해서 모든 지표를 정확히 측정할 수 있는 것은 아니다.

특히 단일 근거 질문과 여러 근거가 필요한 multi-hop, comparison 질문을 구분한다. MRR은 첫 번째 관련 결과의 순위만 평가하므로 여러 정답 근거의 완전성을 나타내는 지표로 사용하지 않는다.

## Golden 데이터셋의 근거 매핑을 최우선으로 검증

**이 작업이 이번 개선에서 가장 중요하다.**

현재 사용하는 새로운 Golden 데이터셋은 다음 파일이다.

- `golden_dev.jsonl`
- `golden_test.jsonl`

먼저 실제 파일의 스키마를 분석하고, 정답 문서 ID, 근거 텍스트, 근거 청크 ID 등의 존재 여부와 의미를 확인한다.

이후 실제 RAG 검색 인덱스와 연결하여 다음 사항을 검증한다.

1. Golden 데이터셋의 정답 문서 ID가 실제 검색 인덱스의 문서 ID와 일치하는가?
2. Golden 데이터셋의 근거 텍스트를 실제 청크와 정확하게 매핑할 수 있는가?
3. 질문에 필요한 근거가 여러 개일 때 각 근거를 개별적으로 식별할 수 있는가?
4. 표 해석, 수치, 조건, multi-hop, comparison 유형에서 근거 매핑이 올바르게 작동하는가?
5. 전처리 과정에서 원문과 청크의 텍스트가 달라진 경우 어떻게 매핑할 것인가?

문서 단위 검색 성공과 청크 단위 근거 검색 성공은 반드시 구분한다.

예를 들어, 정답 문서에 포함된 관계없는 청크 하나를 검색했다고 해서 정답 근거 검색에 성공했다고 판단해서는 안 된다.

가능하다면 기존 청크 ID와 원문 출처 메타데이터를 이용해 정답 근거를 연결한다.

근거 ID가 직접 존재하지 않는 경우에는 텍스트 정규화, 원문 구절 매칭, 관련 메타데이터 등을 활용한 결정적 매핑 방식을 검토한다.

단, 다음 원칙을 지킨다.

- 임의의 의미 유사도 임계값만으로 정답 청크를 확정하지 않는다.
- 동일한 문구가 여러 청크에 존재할 수 있다는 점을 고려한다.
- 매핑이 불확실하면 임의로 정답 라벨을 생성하지 않는다.
- 매핑 성공률과 실패 사례를 별도로 보고한다.
- 청크 매핑 정확성을 샘플링하여 검증할 수 있어야 한다.

최종적으로 **문서 단위 Recall@k/MRR과 청크 단위 Recall@k/MRR의 구현 가능 여부를 구분**하고, 신뢰할 수 있는 지표만 실제 평가에 사용한다.

## 실제 검색 파이프라인의 특성 반영

현재 Retriever는 일반적인 고정 Top-k 검색만 수행하는 구조가 아니다.

하이브리드 검색, 문서 라우팅, 요구사항 코드 기반 검색, 중복 청크 제거, 토큰 예산 기반 컨텍스트 선택 등이 적용되어 있다.

따라서 다음 두 가지를 구분해서 평가한다.

**A. 검색 순위 평가**

검색 후보의 순위를 기준으로 Recall@k, MRR@k 등을 계산한다.

**B. 실제 RAG에 전달되는 컨텍스트 평가**

최종적으로 LLM에 전달된 청크에 정답 근거가 얼마나 포함되었는지 평가한다.

검색 순위가 높더라도 토큰 예산 제한으로 해당 청크가 제외되었다면 실제 답변 생성에 사용될 수 없다는 점을 고려한다.

평가에 사용한 검색 설정, k 값, 토큰 예산을 결과에 기록한다.

기존 Retriever의 검색 동작을 평가 구현을 위해 임의로 변경하지 않는다.

## Generation 및 Grounding 평가 간소화

LLM 기반 RAGAS 지표는 우선 다음 두 가지를 유지하는 방향으로 검토한다.

**Faithfulness (Grounding)**

- 생성된 답변이 실제 검색된 컨텍스트에 의해 뒷받침되는가?
- 검색된 근거에 없는 내용을 생성하거나 근거를 왜곡했는가?

**Factual Correctness (End-to-End)**

- 생성된 답변이 Golden 데이터셋의 정답과 사실관계상 일치하는가?
- 수치, 조건, 날짜, 요구사항 등이 정확한가?

기존 `answer_relevancy`는 다른 평가 지표와 일부 목적이 겹치며 추가 LLM 호출 비용이 발생하므로 기본 평가에서 제외하는 방향으로 검토한다.

다만 Faithfulness와 Factual Correctness가 서로 다른 품질을 평가한다는 점을 유지한다.

- Faithfulness가 높아도 잘못 검색된 문서에 근거했다면 최종 정답은 틀릴 수 있다.
- Factual Correctness가 높아도 검색 근거 없이 답변했다면 Grounding에 문제가 있을 수 있다.

기존 자체 지표인 `key_facts_in_answer`, `key_facts_in_context`는 유지하는 방향으로 검토한다.

단, 문자열 기반 핵심 사실 일치가 의미적 정답 판정과 동일하지 않다는 한계를 명확하게 구분한다.

## 최종 평가 구조

목표 평가 구성은 다음과 같다.

| 영역 | 지표 | LLM 필요 |
|---|---|---|
| Retrieval | Recall@k | X |
| Retrieval | MRR@k | X |
| Retrieval 근거 검증 | Evidence Coverage | X (규칙 기반 구현 시) |
| Grounding | Faithfulness | O |
| End-to-End | Factual Correctness | O |
| 운영 성능 | Latency, Tokens, Cost | X (추가 Judge 호출 없음) |

단, 위 구성은 확정 사항이 아니라 목표안이다.

실제 Golden 데이터셋과 검색 결과를 분석해 계산 가능성과 유효성을 검증한 후 최종 지표를 결정한다.

중복되거나 신뢰성이 낮은 지표는 무리하게 유지하지 않는다.
