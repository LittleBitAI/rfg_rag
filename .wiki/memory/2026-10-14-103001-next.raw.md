## How the parsing is structured

There are three layers, each linked to the one above it.
- **Record:** the cleaning unit, one per HWP paragraph block (`body`, 18,154) or PDF page (`page`, 5,588). Text moves from `raw_text` to `clean_text` to `search_text`. Each record also carries requirement IDs, image links, a review status and exception kinds.
- **Element:** the structural unit. Kinds are `paragraph` 11,935, `table` 14,030, `toc` 56 and `image_text` 19. Tables keep cells with row/col/rowspan/colspan. However, their coordinate system is declared as "observed markdown logical rows, not original cells", so it is not the original HWP grid.
- **Chunk:** points back to its elements with character offsets (`spans`). It has `payload` (the text that gets embedded, sometimes with a context header) and `body` (the text that is shown).
  - Types: `table` 8,630, `requirement_detail` 5,101, `prose` 4,933, `requirement_summary` 309, `image_ocr` 13, `image_text` 6.
  - Requirement chunks carry a `requirement_key` such as `SFR-001`.
  - Size in o200k tokens: median 177, 95th percentile 789, maximum 800.

For comparison, this repo's ① cuts 700-character chunks of kind `text`/`table`/`image_caption`. The current local output is 18,988 chunks from 100 documents.

## How OCR was done

There are two layers, and only the second reaches search.
- **Raw OCR:** EasyOCR 1.7.2 (Korean + English, CPU) ran on 573 candidate images out of 1,196. Of the rest, 533 were unsupported formats such as WMF and 90 were judged unnecessary. Each image gets per-line pixel bboxes, text and a confidence score. The raw text is often garbled (e.g. `0+ 9.32 / B9 ill 97%1 / 프놈편`). All 573 results are marked `UNVERIFIED` and `search_eligible=false`.
- **Human visual review:** 24 images were picked, 8 each for amounts/figures, mandatory/forbidden items, and system architecture.
  - 12 passed: 4 for all visible text, 8 for declared pixel regions only. The other 12 are on hold.
  - Reviewers rewrote the passed text by hand as structured lines. Example: `전체 개발기간 | … | 9.3개월` / `종합의견 | 적정 사업기간: 10개월`.
  - Of 70 content units, 6 duplicated existing body text and were removed, leaving 64. These were appended as 12 new record/element/chunk sets (`image_ocr`).
  - With 1 earlier result from v10, 13 OCR records are searchable in total.
  - Each keeps `verified_region_text`, `ocr_engine_raw_text`, and `image_source` (HWP stream, picture record, BinData, image SHA). `page` is null and `requirement_key` is null.

## What effect to expect

These are inferences until measured:
- Requirement-level chunks with requirement codes and preserved table structure should help questions like "SFR-001 of X".
- Deduplication drops 2 documents.
- The OCR gain is very small: 13 of 18,984 chunks (0.07%). 560 images are still unverified and 533 are unsupported.

The package reports hit@5 53/54 and recall@20 61/61. Those were measured on 61 development questions using the author's own retriever (a pgvector-based codebase outside this repo). They say nothing yet about this repo's ⑤ scores.

The "71.28%" figure is not a loss rate. It means 217,866 of 305,651 non-empty source units were checked, and 87,785 are simply unchecked. The package also states that the full raw → final pipeline is not reproducible (`whole_raw_to_final_reproduced: false`).

These problems would surface on `main`:
- **Embedding length:** `main` has `max_seq_length: 512`, while the package config uses 2048. Chunks go up to 800 o200k tokens, so the end of long chunks probably won't be embedded. BM25 still indexes the full text.
- **Page numbers:** `page` is null for 18,690 of 18,984 chunks (98.5%). Source cards would show only the file name.
- **Kind labels:** in ④, `requirement_detail` is labelled "본문" (body text), because only `table` and `image_caption` have their own labels.
- **ID changes:** doc and chunk IDs change, so the existing `eval_set.jsonl` (made from the old chunks) has to be rebuilt starting from ③.
- **Python version:** `adapt_v11.py` uses `hashlib.file_digest` and needs Python 3.11+. The repo runs on 3.10.
- **File size:** the adapted `chunks.jsonl` is 134 MB, over GitHub's 100 MB limit. It has to live under `data/` (git-ignored) and be shared the same way `data/` is.
- **OCR rule:** CLAUDE.md forbids a local OCR model. Using EasyOCR's saved outputs as data is fine, but its OCR code must not be brought in.
