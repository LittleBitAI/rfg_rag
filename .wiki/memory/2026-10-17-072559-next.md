# OCR for labelled images: benchmark PaddleOCR-VL-1.5 against API models, then write a sidecar JSONL that 01 reads (PR #61 merged)

The user wanted OCR text for the images picked in the frontend OCR labelling screen (data/ocr_labels). The plan benchmarks local PaddleOCR-VL-1.5 (run over SSH) against gpt-6-luna and gemini-3.5-flash-lite to see whether a local model is good enough or a frontier model is needed. The output must be JSONL that matches the existing preprocessing format. The user settled the rule conflict, ownership, scope, reference method, metrics, decision rule and output placement, and the assistant wrote one combined spec. The work landed as PR #61 (merged; round 4; no P2 items left).

## Decisions

- Rewrite the CLAUDE.md OCR rule so each image type's engine is chosen by measured quality and measured cost per image on the reference set. The rule names three allowed engines (PaddleOCR-VL-1.5, gpt-6-luna, gemini-3.5-flash-lite) and requires every paid OCR call to be logged with its cost. Gemini pricing is tracked too. — If Gemini turns out very cheap and also accurate, that gives a legitimate reason to choose it. The user asked that the doc state this as a rule rather than quote their words. (rejected: Keeping the old rules: images become text only through the OpenAI API (LLMImageBlobParser), and no local OCR model or VLM)
- Change rag/preprocessing so 01_preprocessing.ipynb reads the OCR results JSONL, even though OCR belongs to the preprocessing owner (rejected: Leaving the label reading to the preprocessing owner)
- Scope is images labelled 1 (must recognize) and 2 (hard to recognize): 320 distinct images (rejected: Including label 3 (not needed))
- The coding agent builds the reference by viewing the images itself and writing the reference text (up to 10 images per image type × label group) — The writing agent (6.1 sol) is a highly capable model (rejected: Human-written reference transcriptions)
- Metrics: edit similarity (1 − CER), key-token recall and precision (using the repo's existing key-fact string matching), and cost, latency and empty-output rate per image
- Decision rule per image type: the local model wins a type if its key-token recall is within 5 points of the best API model and its precision is not lower
- Output placement: a sidecar JSONL keyed by image_sha256 + occurrence. 01 reads it to emit image_caption records (rejected: Inserting OCR into the parser output directly)

## Facts

- Existing OCR insertion format: parser record {"page", "kind": "image_caption", "text": "[그림/도표 설명] …"} placed where the image sits; chunks.jsonl rows have chunk_id, doc_id, source, title, doc_type, page, kind, section, text, body (unverified)
- chunk_id is sequential per document ({doc_id}::c00012), so inserting image captions shifts every later chunk ID (unverified)
- The labelling screen records one label per occurrence (place). Latest label per place: 1,040 places, of which 194 are label 1, 197 are label 2 and 649 are label 3 (unverified)
- 391 places (342 HWP, 49 PDF) need OCR, covering 320 distinct images. All of them open, and none also appears in a place labelled 3 (unverified)
- 80 HWP places have marker_start null (no position in the body), so 01 did not see them before (unverified)
- Label rows carry doc_id, image_name and marker_start per occurrence (unverified)
- The OCR model configured before this work was gpt-5-mini (unverified)
- Team VM for local OCR: codeit (NVIDIA L4), reached over SSH (unverified)
- Spec choices: Gemini is called via the openai package through Gemini's OpenAI-compatible endpoint, and the existing usage logger records its cost. PaddleOCR-VL-1.5 runs in its own environment on codeit, so requirements.txt is unchanged. The OCR results file lives in data/, not artifacts/. 01 makes no API calls when it reads the file. Unplaced HWP images are appended at the end of the document (unverified)

## Preferences

- Do not write the user's reasoning verbatim into docs; infer it and edit the documents as rules
- Run local OCR over SSH
- The final parsed JSONL must match the existing preprocessing pipeline format, to avoid format conflicts

## Open

- With about 10–20 reference images per type, a 5-point gap is near noise; near ties should be read as ties
- Prices and exact API IDs for gpt-6-luna and gemini-3.5-flash-lite were not confirmed
- Whether PDF occurrences in the labels carry a page number was not checked
- The assistant's self-settled details (appending the 80 unplaced HWP images at the end, Gemini via the OpenAI-compatible endpoint, the results file in data/) were offered as overridable and never explicitly confirmed by the user
