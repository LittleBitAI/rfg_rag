# Adopted preprocessing owner's v11 RFP dataset via a loader in rag/preprocessing and ported feature/Retrieval onto dev (PRs #19, #21 merged)

The user asked for a full survey of the preprocessing owner's delivered folder (v11 dataset, retriever-compatibility adapter, test notebook), how its parsing and OCR are structured, how it relates to PR #12, and whether it works as intended. They chose four things: a small loader in rag/preprocessing plus a switch in notebook 01, a side-by-side ⑤ comparison on the same eval set, max_seq_length raised to 2048, and porting the retrieval owner's branch as a separate spec on a separate branch. Both were implemented and merged: PR #19 (v11 input, 2048 embedding length, ⑤ side by side) and PR #21 (feature/Retrieval changes from 1ed2d72 ported onto the current retriever). PR #13 was also merged.

## Decisions

- Adopt v11 data with a small loader in rag/preprocessing and a switch in 01_preprocessing.ipynb, rather than merging the external pipeline code
- Acceptance is a side-by-side ⑤ comparison of the current parser and v11 on the same frozen question set — Questions generated by 03 from chunks would differ per input, so each variant would be scored on a different question set; the hand-written golden questions are used instead (rejected: questions generated by 03 from chunks)
- Raise embedding.max_seq_length from 512 to 2048 — v11 chunks go up to 800 o200k tokens, so the tail of long chunks would not be embedded at 512 (rejected: keep 512)
- Port the retrieval owner's feature/Retrieval version (commit 1ed2d72) as a separate spec on a separate branch — User asked that the specs be split, i.e. separate branches (rejected: one combined branch/spec)
- Branches use feature/<topic> into dev: feature/preprocessing-v11-input and feature/retrieval-port — dev/feature/... cannot be created because branch dev exists; teammates use feature/<topic> (rejected: dev/feature/...)
- Port keeps question rewriting (search(question, query=...)) and per-agency interleaving, while switching result cutoff from top_k to token_budget — feature/Retrieval was cut before question rewriting (#6)

## Facts

- PR #19 merged: 01_preprocessing.ipynb can load chunks.jsonl/docs.jsonl from the v11 package via a loader in rag/preprocessing; embeddings use max_seq_length 2048; ⑤ results for the current parser and v11 are shown side by side on the same question set. README.md and PR credit Se hui Hwang (@hwangsiiii) for the v11 package and integration idea.
- PR #21 merged: the retriever on dev includes feature/Retrieval changes from commit 1ed2d72 (requirement-code exact match and code tokens in BM25, Kiwi user words, aliases and negation tokens, token_budget packing with near-duplicate removal, org_csv-assisted agency routing, TOC regex fix in parsing.py) while keeping question rewriting and per-agency interleaving; ⑤ shown before and after on the same question set.
- PR #13 merged.
- git cannot create refs/heads/dev/feature/x because a branch named dev exists; team convention is feature/<topic> with PRs into dev (feature/Generation, feature/Retrieval, feature/preprocessing, feature/question-rewrite); PR #3 with dev-feature-ssh-gpu-workspace was closed (unverified)
- v11 package (RFP_Preprocessing_Final_v11_Team) covers 98 documents (100 originals minus duplicates): final_records.jsonl 23,761, final_elements.jsonl 26,040, final_chunks.jsonl 18,992 (unverified)
- Parsing layers: record (HWP paragraph block body / PDF page; raw_text→clean_text→search_text) → element (paragraph/table/toc/image_text; table cells are observed markdown logical rows, not original HWP grid) → chunk (spans offsets back to elements, payload embedded, body shown; types table, requirement_detail, prose, requirement_summary, image_ocr, image_text; requirement_key like SFR-001; max 800 o200k tokens) (unverified)
- OCR: EasyOCR 1.7.2 raw output on 573 of 1,196 images is all UNVERIFIED and search_eligible=false; only 13 human-verified image_ocr records are searchable (0.07% of chunks), with page and requirement_key null (unverified)
- adapt_v11.py in RFP_v11_Retriever_Compatibility outputs chunks.jsonl (18,984 chunks, 134 MB), docs.jsonl (98), tables.jsonl, chunk_mapping.jsonl; it uses hashlib.file_digest (Python 3.11+) while the repo runs on 3.10 (unverified)
- Adapted chunks.jsonl (134 MB) exceeds GitHub's 100 MB limit and must live under git-ignored data/ (unverified)
- In v11 chunks page is null for 18,690 of 18,984 (98.5%), so source cards show only the file name; doc/chunk IDs change so eval_set.jsonl must be rebuilt from ③ (unverified)
- The package states the full raw→final pipeline is not reproducible (whole_raw_to_final_reproduced: false); the 71.28% figure is checked-coverage (217,866 of 305,651 units), not a loss rate (unverified)
- PR #12 (hwangsiiii, feature/preprocessing → dev) adds documentation notebooks under preprocessing/ that import modules absent from this repo and violate CLAUDE.md §4; using v11 data does not require merging it (unverified)
- CLAUDE.md forbids a local OCR model; using saved EasyOCR outputs as data is fine but OCR code must not be brought in (unverified)
- Golden comparison questions: eval/golden_set.jsonl (15 questions) and eval/eval_questions.yaml (unverified)
- feature/Retrieval opens data/data_list.csv without a check; the user's data/ had only rfp.zip (unverified)

## Preferences

- Do no unnecessary implementation (쓸데없는 구현은 하지말아라).
- Survey everything in a provided folder exhaustively (전부 전수조사).
- Check how teammates named their branches before creating one.
- Split specs into separate branches when they cover different concerns.
