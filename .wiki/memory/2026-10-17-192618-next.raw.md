The pipeline can only fetch a few text passages that look similar to the question. No part of it stores a budget per project.

## Why the answer says "not found"

1. Search returns the wrong kind of passage. The question names no agency, so the agency router searches the whole collection. The hybrid ranker (keyword search plus embedding similarity) then returns the passages that look most like "사업 예산 1억원 이상 … 개요". The passages that contain the literal phrase "1억원 이상" are mostly threshold rules, not budget statements. The answer you got shows exactly these:
- an evaluation committee size table,
- a definition of "SW 사업 of 1억원 or more",
- a guarantee-rate band.

The model was told to use only what it was given, so it correctly said it could not find a list and offered these near-misses.

2. Nothing records a budget for each project.
- `docs.jsonl` holds the title, cover and opening text, but no budget.
- `data/data_list.csv` has only two columns: `파일명` (file name) and `발주기관` (ordering agency).
- Chunks do carry `recognized_fields` entries tagged `money`, but they are unlabelled amounts like "80만원", and no code in `rag/` reads them.

3. Even perfect search could not fit the answer. The context limit is `token_budget: 2500`, which is about 5–10 chunks. A full answer needs one budget line plus one overview for every qualifying project.

4. The budgets are in the documents. I ran a rough regex check: a budget label (사업예산, 사업금액, 소요예산, 추정가격, …) followed by an amount appears in 60 of the 98 documents. 45 of those state the amount as a full won figure, and 28 of the 45 are 1억원 or more. The check is also imprecise: some first matches are thresholds, such as "추정가격 2천만원 이상…". So how the budgets get extracted is the main decision below.

## Shape of the fix

1. Preprocessing stores one budget per document in `docs.jsonl`: the amount in won, the original text, and the chunk it came from.
2. Retrieval adds a deterministic route for questions like "예산 N원 이상/이하/초과/미만". This route skips top-k ranking. It returns every qualifying document's budget chunk and its overview chunk, ordered by budget, under a separate token limit.
3. The answer says how many documents had no recognisable budget and were left out. That way "all projects" is never silently partial.

Questions without an amount filter keep exactly today's search results. This touches two owners: preprocessing (pipeline 1) and retrieval (pipeline 2).

Two decisions shape the spec: where the budget figures come from, and how wide the question coverage is. A third covers how the answer handles a long list.

## 답 · 2026-10-17 09:43 · unverified

Metadata filtering can be built with no fixed unit list and no LLM calls. The repository already contains the parser it needs. `golden_pipeline` has a Kiwi-based quantity reader, `facts()`. It gets the unit from the part-of-speech tags that follow a number, not from a list of known units, and it multiplies the numeral words 십/백/천/만/억/조 together. For each amount it also returns the words just before it (the "subject"), which serves as a field label. I ran it locally on a few sample phrases:

| Input | Parsed (value, unit, subject) |
|---|---|
| 사업예산 : 금 130,000,000원 | 130000000, 원, {금, 사업, 예산} |
| 총 사업비 1억 3천만원 | 130000000, 원, {사업비} |
| 소요예산 130백만원 | 130000000, 원, {소요, 예산} |
| \| 사업금액 \| 717,285,200원 \| | 717285200, 원, {금액, 사업} |
| 사업기간: 계약일로부터 8개월 | 8, 개월, {계약, 기간, 사업, 일} |
| 사업 예산 1억원 이상인 사업들 (the question) | 100000000, 원, {사업, 예산} |

So "1억 3천만", "130백만" and "130,000,000" all become the same number, and other kinds of values (months, people, counts) parse the same way. The scoring code in `rag/evaluation/evaluation.py` also parses numbers, but it uses a fixed unit list, so it is the wrong base for this.

## Design

1. Indexing. When the index is built, every amount in every chunk is saved as a metadata row: document, chunk, value, unit, subject words, and the original text. If the amount is followed directly by a comparison word (이상/이하/초과/미만/이내/까지), it is marked as a threshold, not a value of the document. This is what removes clauses like "추정가격 2천만원 이상인 사업은…". Comparison words are part of the question grammar, not units.
2. Reading the question. At search time, the same parser reads the question. If it finds a comparison and no agency is named, the question takes the filter route:
   - one amount + 이상/이하/초과/미만 → a threshold,
   - two amounts with the same unit (~, 사이, 부터…까지, 이상…이하) → a range,
   - 가장/최대/최소 + 큰/많은/작은/적은 → the largest or smallest value.

   Questions with a document-name prefix still route to that document as they do today. Every golden dev question carries such a prefix, so dev search results should not change.
3. Matching the field. A value counts only if its unit is the same as the question's and its subject means the question's subject. For each document, the best-matching value is used, and documents are filtered and sorted on it.
4. Overview. For each qualifying document, the existing hybrid ranker runs inside that document alone, using the rest of the question ("그 사업들의 개요"). That way "overview" is not hard-coded either.
5. Compact context. Each qualifying document sends its value line plus a trimmed overview, under a separate token limit. The context also says how many documents had no matching value, so the answer can say they were left out.

Two choices are still open, and the done conditions depend on them. First, how to decide that 예산, 사업비, 사업금액 and 추정가격 all mean "budget" without a synonym list. Second, where the parser should live, given that `golden_pipeline` is deliberately kept separate from `rag/`.
