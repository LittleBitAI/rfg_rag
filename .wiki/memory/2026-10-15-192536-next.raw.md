## 답 · 2026-10-15 16:30 · unverified

This can be built as a frontend-only tool. One limit shapes it: the backend already has everything needed to find images and record where they came from, but nothing in it saves the images where a screen could show them.

**What can be reused**

- **Image screening and location records.** PR #31 added a CRAFT screening step (a text-region detector, off by default) in front of the paid Vision OCR. It records each image's source and location in `artifacts/ocr_selection.jsonl`:
  - document SHA, file name, `format`
  - for HWP: `image_name`, `marker_start`, `repeated_occurrences`
  - for PDF: `page`, `image_index`, `xref`, `bbox_points`

  However, it writes each image to a temporary folder that is deleted afterwards, so the image itself is gone.
- **Getting the images out.** `_hwp_raw_text(path, image_dir)` already saves HWP images to a folder and leaves `[IMAGE: name]` markers in the text. PDF images come from PyMuPDF's `page.get_images()` and `get_image_rects()`. A small extraction script can call these read-only, together with `collect_inputs` and `make_doc_id`, and write the same location fields. No file under `rag/` changes.
- **The v11 package images.** These can't be the image source. Its manifest lists 1,196 images, but only 13 asset files are actually in the local copy.

**Frontend language**

Use the stack the question screen already uses: React + Vite in the browser and a thin FastAPI server in Python. This adds no new packages to `requirements.txt` or `package.json`, the design stays fully flexible in CSS, and the server can import backend functions directly. Streamlit or Gradio would be a new dependency and much harder to style.

**Keeping folders apart**

- Code goes in `frontend/ocr_select/` (extraction script, server, launchers). The question screen's `server.py` and `App.jsx` stay as they are.
- Outputs go in `artifacts/ocr_labels/`, which is already ignored by git. The name deliberately differs from CRAFT's `ocr_selection.jsonl` / `ocr_review.jsonl` / `ocr_detector/` so the two never mix:
  - `images/<doc_id>/…png` for the images
  - `images.jsonl` for each image's source and location
  - `labels.jsonl` for the 1/2/3 decisions

**Things to know**

- **Section 4 of `CLAUDE.md` needs an edit.** It currently defines the frontend as "the question screen … wraps `answer_question`", so the frontend row has to be widened. That is a rules change inside your own pipeline.
- **The labels can't steer OCR yet.** Making `01_preprocessing.ipynb` OCR only the images labelled 1 would mean editing preprocessing, which you've ruled out. So the deliverable stops at a labels file keyed to the same location fields. Wiring it into 01 would be the preprocessing owner's change.
- **Some images can't be shown.** Browsers can't display HWP vector images (WMF/EMF). An earlier session counted 533 images in unsupported formats; that count is unconfirmed.
- **Branch name.** Teammates use `feature/<topic>` with PRs into `dev`, for example `feature/craft-pre-ocr-selection-clean`, `feature/golden-split` and `feature/Retrieval`. `dev/...` names are impossible because a branch named `dev` exists. I'd suggest `feature/ocr-image-labeling`, cut from the latest `origin/dev`.

## 답 · 2026-10-15 16:36 · unverified

All five decisions are made, so the task is fully specified. It's a single piece of work that stays inside the frontend pipeline. The one exception is a single line in the repository rules: the frontend row in section 4 currently says the frontend only wraps `answer_question`, so that row is widened.

Here is how the pieces fit:

- **Extraction.** A one-off extraction script reuses the preprocessing functions that already pull images out of HWP and PDF files. It saves each image under `artifacts/ocr_labels/` along with the same source and location fields that the CRAFT screening step writes. It doesn't edit `rag/`.
- **Server.** A small FastAPI server lists the images, serves the image files and records labels.
- **Labelling page.** A second Vite page shows one card per distinct image, lists every place the image appears, and takes a 1/2/3 label.
- **CRAFT badge.** When `artifacts/ocr_selection.jsonl` exists, the card shows CRAFT's verdict as a badge. The match is by document and location, not by image hash, because CRAFT hashes its own re-encoded copy of the image. If CRAFT logged the same location more than once, the latest row wins.
- **Unviewable images.** WMF/EMF files and images that fail to decode get a placeholder card that can still be labelled. An earlier, unconfirmed count put 533 images in unsupported formats like these.

The labels file is the end product. Making `01_preprocessing.ipynb` OCR only the images labelled 1 is left for a separate change by the preprocessing owner. Until then, the labels don't change how the documents get parsed.
