# rfg_rag restructured into five pipelines with Korean top-level guidelines (PR #1, PR #2 merged)

The user asked to restructure and refactor the rfg_rag repository (a RAG system for RFP documents) and to make notebook execution structural, under strict top-level rules: no useless code, Korean documents and comments. Two specs were settled and merged. `korean-top-level-guidelines` (PR #1) added CLAUDE.md, an identical AGENTS.md and a ruff complexity limit. `four-pipeline-refactor` (PR #2) split the code into five pipelines (preprocessing, retrieval, validation, generation, evaluation), deleted everything else and the dependencies only that code needed, and added Langfuse Cloud tracing. The merged PR #2 reportedly also attaches evaluation scores to Langfuse traces, although the user had chosen tracing only.

## Decisions

- Top-level guideline files: CLAUDE.md written in Korean, an identical AGENTS.md, and a ruff complexity limit as the only mechanical enforcement — A previous repository on the same project (project-codeit-mid) was abandoned because its code grew too complex, so the rules against unnecessary code have to live in the top-level guidelines
- Documents, comments and docstrings are in Korean in this repository, and the guideline file states that it overrides the wiki-agent hub's English rule here — The user required Korean. The hub keeps sending its English-comments rule to every session, so mixed-language files would result unless the override is stated outright (rejected: English comments and documents, as the hub rule asks)
- The guideline branch merges before the refactor branch — The refactor branch is then written under the new rules
- Five pipelines, each with its own owner: preprocessing (HWP and PDF parsing, chunking, OCR), retrieval (indexing and search over the chunk files), validation, generation, evaluation — These match the team members' roles. The user added preprocessing as a separate owner (rejected: The old layout of three notebooks and six roles)
- Validation means building and checking the evaluation dataset
- One notebook per pipeline. Logic lives only in modules, and notebooks hold only config, calls and display
- Refactor depth: keep only what the five pipelines need
- OCR keeps only the `llm` (OpenAI vision) backend. It is off by default, with one flag in the notebook to turn it on (rejected: The `hf-vlm`, `rapidocr` and `tesseract` backends)
- Dependency cleanup goes inside the refactor spec. Every package left in requirements.txt must be imported directly by rag/ or the notebooks, except torch and ruff. A package is added only if this repository's code imports it directly — Which packages are unnecessary depends on which imports survive the refactor (rejected: A separate cleanup branch)
- Evaluation is split into four categories: Retrieval, Generation, Grounding and End-to-End — The user wanted evaluation broken down rather than reported as a single score (rejected: A single undifferentiated evaluation)
- Langfuse Cloud is used for tracing only, viewed by the user alone on the web. Teammates see the retrieval and generation evaluations in notebooks and files — Sending scores to Langfuse would require a trace id in generation's answer file and a Langfuse import in evaluation, which couples two pipelines (rejected: Sending the four evaluation scores to Langfuse)

## Facts

- PR #1 (`korean-top-level-guidelines`) was merged after review round 4 with 0 P2 findings left.
- PR #2 (`four-pipeline-refactor`) was merged after review round 2 with 0 P2 findings left; all 16 done conditions passed.
- After PR #2, each pipeline has its own `rag/<pipeline>/` package and a notebook that only calls it; everything else and every dependency only that code needed was deleted.
- After PR #2, OCR uses OpenAI vision behind one flag that is off by default.
- After PR #2, when the owner's keys are present, each answered question is one Langfuse Cloud trace (retrieval and generation, with model, tokens and cost), and the evaluation scores are attached to that trace.
- The project is a RAG system for RFP documents: PDF and HWP input, FAISS/BM25 hybrid search, gpt-5-mini, and RAGAS for evaluation (unverified)
- Notebook order follows the data flow: 01_preprocessing, 02 retrieval, 03 validation, 04 generation, 05_evaluation.ipynb (unverified)
- Evaluation metric mapping: Retrieval uses context_precision, context_recall and a key_facts-in-chunks check; Generation uses answer_relevancy and a key_facts-in-answer check; Grounding uses faithfulness; End-to-End uses factual_correctness plus latency, tokens and cost. All four are computed from a single run (unverified)
- Evaluation results go to tables in 05_evaluation.ipynb and to four CSV files under artifacts/ (unverified)
- eval/golden_set.jsonl has 15 questions with `reference` and `key_facts` but no evidence chunk ids, so Recall@k and MRR are not possible without labeled evidence chunks (unverified)
- `langchain-community==0.3.31` stays pinned because `ragas==0.4.3` imports a module that was removed in community 0.4 (unverified)
- Langfuse requires the three `LANGFUSE_*` keys in .env. Without them the notebooks run exactly the same (unverified)
- Notebooks have no pip install cell; installation instructions are in the README (unverified)
- The chatbot (03_chatbot.ipynb, app.py Gradio UI, main.py CLI including embedding fine-tuning) and vision.py were slated for deletion under 'keep only what the pipelines need' (unverified)
- On the guideline branch the test rule was softened to forbid only 'useless verification', meaning tests with no behavior to protect, and a wiki-agent gate with a smoke test was added (unverified)

## Preferences

- Useless exception handling, test code and similar must never be added; code must be clean and very easy for a person to read.
- Complex functions are strictly forbidden.
- Unnecessary implementation must never be done, and this rule must be in the top-level guidelines.
- Document generation and comments must be in Korean, specified in the top-level guidelines.
- Langfuse is viewed only by the user, on the web; teammates look at the retrieval and generation evaluations instead.

## Open

- Merged PR #2 reportedly attaches evaluation scores to Langfuse traces, but the user chose tracing only. It has not been checked whether this deviates from the decision.
- Recall@k and MRR rank metrics would need validation to label evidence chunks first; they were left out because nobody asked for them.
- The hub's English-comments rule still reaches every session; turning it off for this repository was suggested but not done.
- The slug `four-pipeline-refactor` is outdated now that there are five pipelines.
