# 질문 화면 디자인

```
누가:   RFP 를 검토하는 팀원
무엇을: 제안요청서에 대해 묻고, 답의 근거 문단을 바로 확인한다
성공:   답변의 [n] 을 누르면 답변 옆에 그 출처의 원문 청크가 열린다
```

## 배치

데스크톱 화면이다. 왼쪽 대화 열에서 읽고, 오른쪽 출처 칸에서 근거를 본다 — 근거를 보려고 스크롤하지 않는다.
사이드바(스레드 목록)는 없다 — 대화는 탭 하나에만 있다.

```
┌ RFP 질의응답 ────────────────────────────────────── 새 스레드 ┐  ← 붙는 상단 바
│                    ╭ 질문 말풍선 ╮  │ 출처                      │
│                    ╰─────────────╯  │ 질문 한 줄 (meta)          │
│ ▣ 문서 도우미                        │ 1 파일 이름…        p.176 │  ← 두 줄 카드, 위에 고정
│   답변 본문 … [1] … [2]              │   청크 첫머리…            │
│   …                                 │ ┃ [1] 파일 p.176          │  ← 펼친 청크는 목록 아래
│                    ╭ 다음 질문 ╮    │ ┃ 청크 본문 (표 포함)      │
│ ╭ 이어서 질문하기               ╮    │ ┃ …                       │
│ ╰ Enter 보내기 · Shift+Enter  ↑ ╯    │                           │
└─────────────────────────────────────┴───────────────────────────┘
       ↑ 대화 열 아래에 붙는 입력 상자       ↑ 상단 바 아래에 붙고 따로 스크롤
```

- 채팅 형태인 이유: 질문을 제목처럼 크게 쓰고 답을 그 아래 펼친 판은 "입력 · 출력의 채팅 직관성이 떨어진다"는 피드백을 받았다.
  누가 말했는지가 위치(오른쪽 말풍선 = 나, 왼쪽 이름표 = 문서 도우미)로 바로 보이게 했다. 답변은 말풍선에 넣지 않는다 — 표 · 목록이 긴 답이 좁은 상자에 갇힌다.
- 기다리는 동안 이름표 아래에 움직이는 점 세 개와 "문서를 찾는 중…" 을 보인다. 답이 오면 입력 상자로 포커스를 돌려 바로 이어 물을 수 있다.
- 입력 상자는 글 칸 아래에 안내(Enter 보내기 · Shift+Enter 줄바꿈)와 보내기 버튼을 둔다. 480px 이하에서는 안내를 숨긴다.

- 출처를 답변 옆에 두는 이유: 처음 판(답변 위 카드 격자)은 넓은 화면의 양옆을 비워 두고 근거를 보려면 스크롤해야 해서
  "모바일 같다"는 피드백을 받았다. 옆 칸은 그 폭을 근거에 쓰고, 답변은 그대로 화면에 남는다.
- 출처 칸은 마지막 턴의 출처를 보여 주고, 이전 턴의 `[n]` 을 누르면 그 턴의 출처로 바뀐다. 칸 위의 질문 한 줄이 어느 턴인지 알려 준다.
- 카드는 두 줄(번호 · 파일 이름 · 쪽 / 청크 첫머리)로 위에 고정하고 청크는 목록 아래에 연다. 카드 바로 밑에 펼치면 긴 청크가 다른 카드를 밀어낸다.
  첫머리 줄이 있는 이유: 한 질문의 출처가 같은 파일인 경우가 많고 HWP 는 쪽 번호도 없어서 파일 이름만으로는 카드가 구별되지 않는다.
- 1024px 보다 좁으면 한 열로 접고 같은 카드 · 청크를 답변 위에 보인다.
- 첫 화면 오른쪽 위, 스레드 화면의 `새 스레드` 와 같은 자리에 `설정` 버튼을 둔다. 펼치면 `OCR 이미지 라벨링`, 그 바로 아래 `OCR 결과 검토`가 나온다.

## 글자 단계

네 단계(display · body · label · meta)만 쓰고, 한 단계가 두 가지 뜻을 갖지 않는다.
예전의 question 단계(26px 질문 제목)는 채팅 형태에서 말풍선(body)으로 바뀌어 없앴다 — 질문과 답이 같은 크기여야 대화로 읽힌다.
label 은 "구역 이름"(문서 도우미 · 출처)과 "출처 번호"(칩) 둘 다지만 둘 다 '본문 바깥의 표지'라는 한 가지 뜻이다.
글꼴은 Pretendard 다. 운영체제마다 다른 시스템 글꼴(Windows 맑은 고딕, macOS Apple SD 고딕) 대신 어디서나 같은 모양 · 같은 굵기 단계로 보이게 했다.
동적 서브셋이라 화면에 쓰인 글자 조각만 내려받는다.
굵은 글씨와 표 머리(`strong` · `th`)는 단계가 아니라 강조로 600 을 쓴다 — 답변 안에서는 body, 청크 안에서는 meta 크기.
처음 판의 13px 단계는 "흐리고 작다"는 피드백으로 없앴다. 가장 작은 글자가 15px 이다.

## 색

글자와 바탕은 무채색이고, 강조색(청록)은 근거로 가는 길과 대화의 두 주체에만 쓴다 — 보내기 버튼, `[n]` 칩, 펼친 출처 카드의 테두리,
질문 말풍선(옅은 청록), 문서 도우미 아이콘 · 기다림 점.
그래서 눈이 본문에서 칩으로, 칩에서 카드로 따라간다. 청록 · 파랑 · 무채색 후보 중 청록을 골랐다 (파랑은 답변 속 링크와 겹치고, 무채색은 칩이 묻힌다).

# OCR 이미지 라벨링 화면 (ocr.html)

```
누가:   OCR 대상 그림을 고르는 팀원
무엇을: RFP 문서에서 꺼낸 그림마다 1 꼭 인식 · 2 인식해야 하나 어려움 · 3 필요 없음을 매긴다
성공:   카드의 버튼을 누르면 바로 저장되고, 화면을 다시 열어도 그 라벨이 눌린 채로 보인다
```

질문 화면 첫 화면의 `설정` → `OCR 이미지 라벨링` 으로 들어온다.
질문 화면과 같은 토큰(색 · 글꼴 · 상단 바 · 10px 모서리)을 `src/ocr/ocr.css` 에 그대로 옮겨 쓴다. 글자 단계는 body · label · meta 셋만 쓰고 display 는 쓰지 않는다 — 제목은 상단 바 한 줄이면 된다.

```
┌ OCR 이미지 라벨링      [묶음1|묶음2|…|묶음5] 라벨 12 / 209 [결과 내보내기] ┐  ← 붙는 상단 바
│ 1 꼭 인식해야 함 · 2 … · 3 …  누르는 즉시 저장됩니다. (meta)    │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐            │
│ │  그림    │ │ 미리보기 │ │  그림    │ │  그림    │  ← 220px, 비율 유지
│ │          │ │ 없음·WMF │ │          │ │          │
│ │ 문서 이름│ │ 문서 이름│ │ …        │ │ …        │  ← label
│ │ BIN03.bmp│ │ BIN05.WMF│ │ p.3 · 1번째 그림       │  ← meta, 이 카드의 위치
│ │ CRAFT …  │ │          │ │          │ │          │  ← 있을 때만
│ │ [1][2][3]│ │ [1][2][3]│ │ …        │ │ …        │
│ └──────────┘ └──────────┘ └──────────┘ └──────────┘            │
└────────────────────────────────────────────────────────────────┘
```

- 카드 하나 = 그림이 나온 위치 하나. 같은 그림(반복 로고)도 나온 곳마다 따로 매긴다 — 처음 판(서로 다른 그림 하나에 카드 하나, 505장)은
  v11 패키지의 그림 목록보다 수가 크게 적어 "그림이 줄었다"는 피드백을 받았다. 카드 제목은 문서 이름이고, 그 아래 한 줄이 문서 안의 위치다.
- 팀원 다섯이 묶음 하나씩 나눠 매기고 각자 결과를 내보내 합친다. 그래서 상단 바에 묶음 고르기(이어 붙인 다섯 버튼, 고른 것만 청록) ·
  그 묶음의 진행 수 · `결과 내보내기` 를 둔다. 묶음을 고르기 전에는 카드 없이 "맡은 묶음을 고르세요" 한 줄만 보인다 — 아무 묶음이나 매기다 남의 몫과 겹치지 않게.
  좁은 화면에서는 바가 두 줄로 높아진다.
- 격자는 `minmax(300px, 1fr)` 자동 채움이다 — 1440px 에서 4열(카드 316px), 480px 이하에서 1열.
- 미리보기를 만들 수 없는 그림(WMF · EMF · 디코딩 실패)은 같은 크기의 surface 상자에 "미리보기 없음 · 형식"과 이유를 적는다. 빼 버리면 '필요 없음'과 '본 적 없음'이 라벨 파일에서 구별되지 않는다.
- 강조색(청록)은 눌린 라벨 버튼과 고른 묶음에만 쓴다. 눈이 "이미 매긴 카드"를 훑어 찾는 길이 하나뿐이도록. CRAFT 분류는 비교용 참고라 무채색 배지다.
- 저장하는 동안 그 카드의 버튼은 잠깐 막힌다 — 한 위치의 라벨이 누른 순서대로 파일에 쌓이게. 실패하면 이전 라벨로 돌아가고 카드 아래에 danger 색으로 이유를 적는다.

## 크게 보기

카드의 그림을 누르면 창을 덮는 어두운 바탕 위에 그 그림을 크게 띄운다. 220px 미리보기로는 글자가 있는지 판단하기 어려운 그림이 많아서다.

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │  ← 어두운 바탕: 누르면 닫힘 (Esc 도)
│ (◀) ┌────────────────────────────────────────────────┐ (▶) │  ← 양옆 화살표 · ← → 키
│     │                                                │     │
│     │   그림 — 비율 유지, 창 너비 · 높이 중 먼저      │     │  ← 그림을 눌러도 닫히지 않음
│     │   닿는 쪽까지 키움 (작은 그림도)               │     │
│     └────────────────────────────────────────────────┘     │
│           문서 이름 · p.3 · 1번째 그림                       │  ← 카드와 같은 문서 이름 · 위치, 한 줄
└──────────────────────────────────────────────────────────────┘
```

- 그림 아래 한 줄에 카드의 문서 이름과 위치를 그대로 적는다. 화살표로 몇 장 넘기고 나서도 지금 어느 문서의 어느 그림을 보는지 알게.
- ◀ ▶ 와 ← → 는 지금 묶음의 카드를 격자 순서대로 앞뒤로 넘긴다. 첫 카드에서는 ◀, 마지막 카드에서는 ▶ 를 감추고 키도 멈춘다 —
  돌아 들어가면 묶음 끝을 지나쳐도 모른다.
- 라벨 버튼은 크게 보기에 두지 않는다. 라벨은 카드에서만 매긴다.
- 미리보기 없는 카드(지금은 한 HWP 의 WMF 그림 `BIN0005.WMF`, 1,044곳 중 5곳)는 누를 수 없고 화살표도 건너뛴다 — 키울 그림이 없다.
  WMF 를 PNG 로 바꿔 두는 길은 접었다. Pillow 는 WMF 를 Windows 에서만 그려서, 팀 VM(`codeit`, Linux)에서 그림을 다시 꺼내면 자리표시가 돌아온다.
  자리표시 카드도 라벨은 그대로 매긴다.

## 원본 보기

그림만 보고는 넣을지 말지 정하기 어려울 때 문서 속 자리를 본다. 모든 카드의 위치 줄 옆과 크게 보기의 설명 줄 옆에 `원본 보기` 밑줄 글자를 둔다
(강조색은 라벨 · 묶음에만 쓰므로 둘레 글자색 그대로). 미리보기 없는 WMF 카드에도 있다 — 그림을 볼 길이 이것뿐이다.

- PDF: 새 탭에서 원본 PDF 를 `#page=N` 으로 열어 그 쪽으로 간다. 브라우저의 PDF 보기라 Windows · Mac 모두 같다 (Safari 는 첫 쪽에서 열릴 수 있다).
- HWP: 파일을 열지 않고 그림 표시 앞뒤 본문(앞 · 뒤 1,000자, 줄 단위)을 흰 상자에 띄우고 그 그림의 `[IMAGE: 이름]` 을 옅은 청록으로 칠해 가운데로 옮긴다.
  HWP 에는 쪽 번호가 없어서다 — 쪽은 한컴이 문서를 그릴 때 정해지고, 카드가 아는 것은 정리된 본문 속 글자 위치(`marker_start`)뿐이다.
  한컴 자동화로 그 자리로 옮기는 길은 Windows 전용에 새 패키지가 들어 접었다. 표는 Markdown 글 그대로 보인다.
- 본문에 표시가 없는 HWP 그림(머리말 · 글상자 속 등, 위치 줄이 "본문 표시 없음")은 앞뒤 글이 없어 `원본 보기` 를 두지 않는다.
- 앞뒤 본문 상자는 바깥을 누르거나 Esc 로 닫는다. 크게 보기에서 열었다면 닫을 때 그 그림으로 돌아간다.

```
┌──────────────────────────────────────────────────────────────┐
│        ┌──────────────────────────────────────────┐          │  ← 어두운 바탕: 누르면 닫힘 (Esc 도)
│        │ 문서 이름.hwp · BIN0003.bmp              │          │  ← label
│        │ … 앞 본문 …                              │          │
│        │ [IMAGE: BIN0003.bmp]                     │          │  ← 옅은 청록, 상자 가운데로
│        │ … 뒤 본문 …                              │          │  ← 넘치면 상자 안에서 스크롤
│        └──────────────────────────────────────────┘          │
└──────────────────────────────────────────────────────────────┘
```

# OCR 결과 검토 화면 (review.html)

저장된 전사를 검토하는 팀원이 원본과 전사를 비교하고 그림마다 판정을 저장한다.
같은 그림이 여러 곳에 등장해도 카드 하나로 묶고, 오른쪽에 모든 위치를 나열한다.
기존 색 · 글꼴을 쓰며, 선택된 판정 버튼만 청록으로 표시한다.

```
┌ OCR 결과 검토                 검토 12 / 320       질문 화면 ┐
│ 문서 · 이미지 유형 · 엔진 · 판정 상태 필터                    │
│                        이전  1 / 320  다음                  │
│ 원본 이미지                 │ 저장된 전사                    │
│                             │ 엔진 · 이미지 유형             │
│ 그림 (비율 유지)            │ Markdown 표 · 제목 · 목록      │
│                             │ 모든 등장 위치                 │
│                             │ [OK] [일부 틀림] [틀림]        │
│                             │ 저장 상태                      │
└─────────────────────────────┴───────────────────────────────┘
```

넓은 화면은 같은 폭의 두 칸이며, 원본은 스크롤 중에도 상단 바 아래에 남는다.
800px 이하에서는 원본 다음에 전사를 놓는 한 열이다. 넓은 표는 전사 칸 안에서 가로로 스크롤한다.
판정을 저장하는 동안 버튼 · 필터 · 이동을 잠가 저장 순서를 지킨다. 실패하면 이전 판정과 재시도 안내를 보인다.
필터의 방향키 선택을 방해하지 않도록 선택 상자에 포커스가 있으면 그림 이동 단축키를 적용하지 않는다.
