I can't tell you yet whether a local model is good enough. Nothing in the repository has compared OCR models, so that has to be measured. Two repository rules also need your decision before anyone starts.

Rule conflicts. The repository rules say images become text only through the OpenAI API (LangChain's `LLMImageBlobParser`). They also say not to add a local OCR model or local VLM, because the team decided against running one.
- PaddleOCR-VL-1.5 is a local VLM, so it conflicts with the second rule.
- `gemini-3.5-flash-lite` is not an OpenAI model, so it conflicts with the first.

There is a precedent for a way through: an earlier session treated saved outputs from a local OCR run as data, as long as the OCR code itself did not enter the repository.

So 320 images need OCR, mostly from HWP documents.

Running PaddleOCR-VL-1.5 locally. Running it over SSH on the team VM `codeit` (NVIDIA L4) is straightforward. From general knowledge, not repository evidence: it is a small document-parsing model. It transcribes text and tables and turns charts into tables, but it does not explain what a diagram means.

My expectation (a hypothesis to test). The local model is probably enough for simple tables and text-heavy screenshots. It probably falls short on diagrams and other images that are hard to recognize, where arrows and layout carry the meaning. The likely result is a split: local for some image types, a frontier model for others.

I can't confirm prices or exact API IDs for `gpt-6-luna` or `gemini-3.5-flash-lite`. They need checking before any paid estimate. The currently configured OCR model is `gpt-5-mini`, which would make a cheap baseline that needs no rule change.

How to judge "recognized well". With no reference transcriptions you can't score anything, so you need a small labelled sample: about 30 images, split by type (table, text, diagram) and by label 1 versus 2. Score each model on that sample with:
- Edit similarity (1 − character error rate): how close the output text is to the reference, from 0 to 1.
- Key-token recall and precision for numbers and terms. Recall is the share of the reference's key tokens found in the output. Precision is the share of the output's key tokens that exist in the reference, so it catches invented numbers. This uses the same string matching the repository already uses for key facts.
- Cost, latency and empty-output rate per image, from actual runs.

Matching the existing format. Today the parser inserts OCR text as a record `{"page", "kind": "image_caption", "text": "[그림/도표 설명] …"}` where the image sits in the document. Chunking then writes `chunks.jsonl` rows with `chunk_id, doc_id, source, title, doc_type, page, kind, section, text, body`.

There is a trap here. `chunk_id` is a sequential number within each document (`{doc_id}::c00012`). Inserting image chunks in their original position renumbers every later chunk, and that breaks the gold chunk IDs that retrieval evaluation depends on. So where the OCR text goes is a real design choice, not just a format detail.

The label rows carry `doc_id`, `image_name` and `marker_start` for each occurrence, which is enough to put text back in place for HWP. I haven't checked whether PDF occurrences carry a page number.

Details I settled myself, which you can override:
- The 80 unplaced HWP images: their text is added at the end of the document. Skipping them would quietly drop part of the 320.
- Gemini: called through the `openai` package using Gemini's OpenAI-compatible endpoint. That needs no new package, and the existing usage logger records its cost the same way as OpenAI calls.
- PaddleOCR-VL-1.5: runs on `codeit` over SSH in its own environment, so `requirements.txt` stays unchanged.
- The OCR results file: goes in `data/`, which teammates already copy once, because `artifacts/` is kept separately on each machine. 01 makes no API calls when it reads the file, so teammates without keys can run it.
- Reference sample: the write agent views up to 10 images in each image type × label group and writes the reference text itself, as you chose.

Rule rewrite. Instead of quoting what you said, the CLAUDE.md change states a rule: each image type's OCR engine is chosen by measured quality and measured cost per image on that reference set. The rule names the three allowed engines and requires every paid OCR call to be logged with its cost. That gives cheap-and-accurate Gemini a documented route to being chosen.

Things to expect from the results:
- With about 10–20 reference images per type, a 5-point gap is near the noise level. A near tie should be read as a tie, not a clear win.
- Once 01 runs with the new captions, chunk IDs after each image shift. That means the 02 index and every gold chunk label (03 evaluation sets and golden data) need rebuilding afterwards. This task doesn't do that rebuild.
