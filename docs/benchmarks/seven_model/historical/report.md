# 일곱 임베딩 모델 첫 비교 (385문항, 과거 기록)

이 문서는 일곱 임베딩 모델을 처음 비교한 과거 기록입니다. 측정할 때 코드와 결과 파일의 해시(파일 내용을 확인하는 값)를 남기지 않았기 때문에, 지금의 [측정 규약](../protocol.md)으로 검증됐다고 말할 수 없습니다. 아래 추천은 당시의 결론으로만 읽어 주세요. 이후 dev 408문항 전체로 다시 잰 결과는 [전체 dev 재측정](../full_dev/report.md)과 [문맥 앵커 재측정](../anchor/report.md)에 있습니다. 수치는 당시 로컬 기록을 옮긴 것이며, 이번에 다시 측정하지 않았습니다.

- 당시에는 KURE를 계속 쓰자고 추천했습니다. Kiwi 하이브리드의 청크 Recall@10은 Nemotron(74.46%)이 KURE(73.37%)보다 1.09%p 높았지만, 92문항 중 나은 문항 2개, 못한 문항 1개 차이였습니다.
- KURE는 Recall@20, 근거를 빠짐없이 담는 정도, GPU 메모리, 색인을 만드는 시간에서 유리했습니다. Nemotron은 Recall@10을 가장 중요하게 볼 때의 대안으로 봤습니다.
- 이 측정은 dev 408문항 전체가 아니라 385문항만 썼습니다. 빠진 24문항은 나중에 [전체 dev 재측정](../full_dev/report.md)에서 다시 넣었습니다.
- 서비스의 모델, 가중치, 색인은 바꾸지 않았습니다. 의미 검색만 쓴 점수로 모델을 고르지 않았고, 모든 수치는 이 PC에서 직접 잰 값입니다. 모델 발행자의 공개 점수가 아닙니다.

용어는 [문맥 앵커 재측정의 용어 표](../anchor/report.md#용어)와 같습니다. 이 문서에는 집계 수치와 측정 조건만 적었습니다. 실제 질문·정답·근거, 문항별 결과, 분할 목록은 공유하지 않는 로컬 폴더 `artifacts/seven_model/record/`에만 있습니다.

## 측정 범위

측정 도중 컴퓨터가 멈췄지만, 일곱 모델의 완료 기록, 82개 설정별 결과, 문항·설정 결과 31,570개, 응답 시간 94,710개를 모두 되살렸습니다. 끝난 측정을 다시 돌리거나 덮어쓰지 않았습니다. 설정마다 385문항을 세 번씩 검색했고, 아래 검증 분할의 응답 시간은 194문항 × 3회 = 582번 잰 값입니다.

1단계는 KURE로 고정하고 검색 방법 다섯 가지를, 2단계는 일곱 모델의 의미 검색과 Kiwi 하이브리드를 비교했습니다. 모든 방법을 실험 경로와 서비스 경로에서 각각 쟀습니다. 모델 이름과 버전은 [models.json](../models.json)에, 모든 k별 지표와 주제·분할별 값은 [quality.csv](quality.csv)에 있습니다. 표의 Recall과 Coverage는 %, MRR은 0~1입니다.

### 빠진 24문항

나중에 다시 확인해 보니, 당시 평가 입력에서 빠진 24개는 모두 여러 근거 질문이었습니다. 평가 입력을 고르는 함수(`load_eval_items`, `check_eval_items`)를 dev에 적용하면 408개 중 384개가 남고, 빠진 24개는 모두 "핵심 사실(key_facts) 없음"이 이유였습니다. 핵심 사실은 답변을 채점할 때만 필요하므로, 검색 순위를 평가할 때 질문을 뺄 이유는 아닙니다. 따라서 이 측정을 dev 전체 비교로 보면 안 됩니다. 이 24개를 빼는 것과, 검색한 뒤 정답 청크 표시가 불완전해 채점에서 빼는 것은 서로 다른 단계입니다.

같은 질문이 겹치거나 정답 청크·생성 묶음을 함께 쓰는 질문은 한 그룹으로 묶어 시드 `20261018`로 나눴습니다. 두 분할에 같은 정답 청크는 없지만, 같은 문서의 다른 근거는 양쪽에 있을 수 있습니다. 이 dev는 Kiwi 개발 때 이미 쓴 데이터라 처음 보는 평가 데이터가 아닙니다.

385문항 모두 일반 검색 경로를 탔습니다. 수량 필터가 그대로 있고 모델마다 수량 구절 벡터가 만들어지는 것은 확인했지만, 수량 질문의 품질과 속도, 기준값 0.66이 다른 모델에서도 맞는지는 이 데이터로 확인할 수 없습니다.

세 사례를 골라 살펴보니 반복되는 토큰, 복합어가 쪼개지는 방식, 조사 차이가 순위를 뒤집는 데 영향을 줬습니다. 이 세 사례의 원인을 본 것일 뿐, 띄어쓰기가 언어를 더 잘 이해한다거나 모든 역전의 원인을 밝혔다는 뜻은 아닙니다. 사례별 질문과 순위는 로컬에만 있습니다.

같은 방식으로 튜닝하면 띄어쓰기 + KURE는 두 경로 모두 0.6을 골라 위 표와 같고, Kiwi + KURE는 0.8을 골랐습니다. 서비스 경로에서 R@10은 73.37%로 같고 R@20은 92.39%로 높아졌지만, Coverage는 72.83%로 낮아졌습니다. 튜닝으로 고른 값이 모든 지표를 좋게 하지는 않습니다.

## 당시 추천

Recall@10만 보면 Nemotron이 1위였습니다. 하지만 1.09%p는 작은 차이였고, 다른 지표에서는 KURE가 나았습니다.

| 항목 | KURE | Nemotron |
| --- | ---: | ---: |
| 고른 가중치 R@20 | 92.39% | 91.30% |
| 근거 여러 개, 모두 담은 문항 | 7 / 9 | 6 / 9 |
| GPU 메모리 | 1.25 GiB | 2.64 GiB |
| 색인 만들기 | 141초 | 468초 |

그래서 당시에는 KURE를 계속 쓰는 것을 실용적인 추천으로 두고, Nemotron은 Recall@10이 조금 높은 대안으로 보고했습니다. 통계적으로 의미 있는 차이나 test에서의 우위를 확인한 것은 아닙니다.

Harrier와 dragonkue는 KURE와 비슷했지만 꾸준히 낫지는 않았습니다. Jina는 상업적 이용이 막혀 있고 품질과 속도에서도 바꿀 이유가 약했습니다. Perplexity는 조건 주제에서 나았지만 숫자 주제에서 떨어졌습니다. upskyy는 품질이 낮고 라이선스도 정해져 있지 않습니다. 이 보고서가 상업적 이용을 새로 허가하지는 않습니다.

측정 중 네트워크 연결 시도는 없었고, API 사용 기록과 서비스 색인은 측정 전후가 같았습니다. `config.yaml`, 서비스 모델과 색인, 원본 평가 입력은 바꾸지 않았고, test 실행이나 재작성·답변·채점·OCR API 호출도 없었습니다. 복구한 뒤 저장된 점수를 모두 다시 계산해 맞는지 확인했습니다. 영향받은 테스트 103개가 통과했고 ruff 검사도 통과했습니다.
