# OCR review screen: original image beside rendered parsed text, one card per image, verdicts saved locally, no API calls (PR #62 merged)

The user wanted a frontend screen for checking whether OCR/VLM/LLM-parsed text was parsed correctly. It shows the original image on the left and the already-parsed result on the right, rendered readably instead of as a raw JSON string, and reads saved results without re-parsing. It is reached from the top-right settings menu, under the OCR labeller link. The user chose view plus a saved verdict, one card per distinct image, and no API use at all. PR #62 was merged after review round 2 with 0 P2 issues left.

## Decisions

- Build a review screen that reads existing parsed results and displays them, rather than re-parsing — Re-parsing is less efficient than showing results that already exist (rejected: Re-parsing for the review screen)
- Layout: original image on the left, parsed result on the right, shown in organized readable form (rejected: Showing the result as a hard-to-read JSON string)
- Entry point: a link in the top-right settings menu, placed under the OCR labeller link
- Purpose: view plus a verdict (OK / wrong / partly wrong), and the verdict is saved
- Unit of review: one card per distinct image (320 cards)
- The screen must make no API calls — The text and image are already a tagged pair, so calling an API would be waste

## Facts

- `data/ocr_captions.jsonl` holds 391 OCR transcriptions, one per place an image appears, linked into preprocessing by #61. They cover 320 distinct images: 342 places in HWP files and 49 in PDFs. (unverified)
- Each row in `data/ocr_captions.jsonl` records the document, the position, the engine and the text. Engines: `gpt-6-luna` for 211 diagrams, `gemini-3.5-flash-lite` for 160 tables and 20 text images. None of the texts is empty. (unverified)
- Original images are in `artifacts/ocr_labels/images/` and share `image_sha256` with the captions file, so no re-extraction is needed. The labeller server on port 8766 serves these images. (unverified)
- OCR text is Markdown (headings, bullet lists, `|` tables in 207 of 391), and `react-markdown` plus `remark-gfm` are already in `frontend/web/package.json`. (unverified)
- The top-right settings menu in `frontend/web/src/App.jsx` holds one link, `OCR 이미지 라벨링`, to `/ocr.html`. The review screen is a second link pointing to a new Vite page next to `ocr.html`. (unverified)
- `artifacts/captions.jsonl` (444 rows) holds older captions from the `OCR = True` path. They are keyed only by a 16-character hash, with no document or position, so they cannot be paired with images and are excluded. (unverified)
- PDF tables extracted by `pdfplumber` and plain HWP body text were not OCR'd and have no original image, so the screen covers image-to-text only. (unverified)
- Of the 320 images, 20 appear in more than one place, with the same text, engine and image type in every place. A card shows the text once, lists all places, and saves one verdict per image. (unverified)
- The screen reads only local files, writes verdicts to a local file, and changes nothing in `rag/`, which keeps the frontend's "shell over the backend" rule. (unverified)
- PR #62 was merged after review round 2 with 0 remaining P2 issues.

## Preferences

- No API calls for data that is already paired: "이미 태깅되어있는 텍스트 + 이미지 쌍인데, 뭐하러 api를 호출하냐? 낭비다."
- Show parsed results in organized readable form, not as a hard-to-read JSON string.

## Open

- Navigation was not chosen by the user. The spec used the assistant's recommendation: filters for document, image type, engine and verdict status, plus previous/next buttons and arrow keys. The alternatives, a scrolling list or a raw-text toggle, were left for the user to request.
