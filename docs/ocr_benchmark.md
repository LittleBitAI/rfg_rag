# OCR 유형별 비교 — 준비 상태

2026-10-16 사용자가 55개 기준 이미지의 세 엔진 비교와 명시한 VM 정리를 승인했다.
API 측정을 진행하며 PaddleOCR 실행 환경은 사용자의 후속 선택에 따라 로컬 Windows PC로 바꿨다.
세 엔진의 측정이 모두 끝나기 전에는 유형별 승자를 정하지 않는다. 전체 320개 실행은 아직 승인되지 않았다.

## 입력과 기준 전사

`data/ocr_labels/ocr_labels_batch1.jsonl`부터 `batch5`까지
`frontend.ocr_select.merge.merge`로 합쳤다. 같은 위치는 시간대로 변환한 최신 `labelled_at`이 이긴다.
전체 1,040곳 중 라벨 1·2는 391곳, 서로 다른 이미지 320개이며 HWP 본문 표시가 없는 위치는 80곳이다.
`data/ocr_benchmark/preparation.json`은 입력 파일 해시와 준비 근거를 기록한다.

에이전트가 번호를 붙인 연락판 27개에서 320개를 모두 보고 분류했다.
서식·행과 열이 중심이면 `table`, 문장·메뉴·표지판의 글자가 중심이면 `text`,
연결·차트·지도·구성 관계가 중심이면 `diagram`이다. 표 150개, 글 20개, 도식 150개다.
처음 준비한 18개를 유지하고, 사용자가 선택한 그룹당 최대 10개 범위로 40개를 추가로 전사했다.
58개 초안 중 자필 본문의 일부를 확실히 판독하지 못한 222·224·263번은 후보 호출 전에 제외했다.
불완전한 기준과 더 잘 읽힌 후보 출력을 비교하면 문자 유사도·정밀도가 왜곡되기 때문이다.
이 세 이미지는 전체 320개 실행에서는 제외하지 않는다.
최종 측정 기준은 55개다. 표·도식은 라벨 1과 2에서 각각 10개씩이며,
글은 라벨 1에서 5개와 라벨 2에서 10개다.
유형별 기준 수는 표 20개, 글 15개, 도식 20개다.
후보 출력을 보기 전에 원본 크기로 각각 보고 전사와 핵심어를 썼고 사람의 교정은 받지 않았다.
기준은 `references.jsonl`, 전체 유형은 `inventory.jsonl`, 선택 위치는 `places.jsonl`이다.
작은 목적 표본이므로 전체 320개의 통계적 신뢰구간이나 일반 OCR 성능을 주장할 수 없다.
읽을 수 없는 서명은 추측하지 않았다.
제외된 초안에는 `[판독불가]` 표시가 있었으며, 확정한 55개 전사에는 이 표시가 없다.
확정 집합에도 이미지 배경의 미세 글씨·가려진 서명처럼 판독이 제한되는 부분이 있어 이미지별 `notes`에 남겼다.
후보 실행 전부터 알려진 한계이며, 측정 후 점수를 보고 제외 여부를 바꾸지 않는다.
`preparation.json`에 기준 파일 SHA-256과 이미지별 주의사항을 기록해 측정 전 상태를 고정했다.

## 지표와 선택

`rag/preprocessing/ocr_benchmark.py`에서 표준 라이브러리로 계산한다.
NFC, 대소문자 통일, 연속 공백 한 칸으로 정규화한 뒤
편집 유사도를 `1 − Levenshtein 거리 / 기준 문자 수`로 계산한다. 삽입이 많으면 음수도 가능하다.

핵심어 재현율은 기준 핵심어 중 출력에 단어 경계까지 일치하는 항목의 비율이다.
정밀도 후보는 출력의 숫자·영문 코드, 기준 핵심어를 구성하는 단어, 기준 전사에 없는 단어다.
그중 기준 전사 어휘에 있는 비율을 정밀도로 쓴다. 기준에 없는 숫자·코드·이름의 창작을 벌점으로 반영한다.
의미 판정은 하지 않으므로 띄어쓰기·조사 차이도 오차가 될 수 있으며 표 셀·화살표 관계는 별도 평가하지 않는다.

모델 × 유형마다 이미지별 값을 산술평균한다.
API 모델은 재현율, 정밀도, 낮은 비용 순으로 최상 모델을 고른다.
PaddleOCR의 재현율이 그 모델보다 5%p 이내로 낮고 정밀도가 낮지 않으면 해당 유형은 로컬이 이긴다.
그 외에는 최상 API 모델을 쓴다.
빈 출력은 전사 후 공백을 제외한 글자가 없는 경우다.
PaddleOCR의 달러 비용은 미해당이며 이미지별 초를 기록한다.
초기화 시간은 제외하고 API는 요청 왕복 시간을 잰다.

## 실행과 저장

두 API는 같은 `INSTRUCTION`과 PNG 입력을 사용한다.
Gemini는 기존 `openai` 패키지와 `https://generativelanguage.googleapis.com/v1beta/openai/`를 사용한다.
환경 변수 또는 `.env`의 `OPENAI_API_KEY`, `GEMINI_API_KEY`가 필요하다.
현재 프로세스 환경에서 두 키를 확인했고, 생성 요청 없이 각 제공자의 모델 목록에서 지정 모델 접근을 확인했다.
`run_api`는 응답마다 `record_usage`로 `artifacts/api_usage.csv`에 비용을 추가하고
해시·엔진·전사·시간·종료 사유를 결과 JSONL에 덧붙인다.
자동 재시도는 끄며 저장된 해시·엔진 조합은 재호출하지 않는다.

PaddleOCR는 로컬 Windows PC의 별도 환경에서
`tools/paddle_ocr.py <manifest> <image_dir> <output.jsonl>`을 실행한다.
[공식 파이프라인](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/PaddleOCR-VL.html)의
`PaddleOCRVL(pipeline_version="v1.5")`를 사용하며 프로젝트 환경에는 paddle을 설치하지 않는다.
이 파이프라인은 자유 지시문을 받지 않으므로 내장 인식 과제를 쓴다.
출력에는 `seconds`, `cost_usd: null`을 저장한다.
처음에는 `codeit`에 별도 환경 `~/ocr_benchmark/.venv`(Python 3.12.3)을 만들었다.
캐시 조사 시점의 VM 디스크는 77 GB 중 74 GB 사용, 약 2.6 GB 여유다.
공식 CUDA 12.6용 PaddlePaddle 3.2.1 설치 검토에서 GPU wheel만 1,890.5 MB임을 확인했다.
승인한 정리 후 5.83 GiB가 비었지만 Paddle wheel의 압축 해제 크기만 3.01 GiB이며 별도 CUDA 라이브러리도 필요했다.
시스템 RAM 여유도 1 GiB 미만이어서 이 작업의 설치 프로세스만 중단하고 다운로드한 wheel은 보존했다.
다른 팀원의 GPU 프로세스는 종료하지 않았다.

사용자는 VM 대신 이 PC를 제안한 뒤 네이티브 Windows 실행을 선택했다.
별도 환경은 `C:/Users/dasdk/.venvs/rfg-ocr-vl15`이며 프로젝트 `.venv`에는 paddle을 설치하지 않는다.
이 PC는 RTX 3080 10 GiB, 시스템 RAM 64 GiB이며 조사 시점에 RAM 약 23.8 GiB와 C: 약 88 GiB가 비어 있었다.
GPU 여유는 약 1.8 GiB로 제한되며 기존 Python 노트북·Uvicorn 프로세스는 종료하지 않았다.
실제 로컬 추론 시간은 이 PC의 측정으로 표시하며 VM의 L4 측정으로 해석하지 않는다.
PaddlePaddle GPU 3.2.1, PaddleOCR 3.7.0, PaddleX 3.7.2 설치를 마쳤다.
CUDA 빌드와 GPU 1개 인식을 확인했고 공식 PP-DocLayoutV3·PaddleOCR-VL-1.5 가중치를 다운로드했다.
준비용 `device="cpu"` 파이프라인 초기화가 성공했으며 실제 이미지 추론은 아직 실행하지 않았다.

후속 조사에서 Uvicorn PID 36444는 에이전트의 종료 조작 없이 사라졌고 GPU 여유는 약 4.6 GiB가 됐다.
남은 PID 12816은 VS Code의 `02_retrieval.ipynb` 커널이다.
읽기 전용 변수 조회에서 `index`가 `nlpai-lab/KURE-v1`을 보유한 `HybridIndex`임을 확인했다.
PyTorch의 실제 텐서 할당은 약 1,093 MiB, 예약은 3,176 MiB다.
커널 종료는 메모리 변수를 잃게 하므로 사용자의 요청에 따라 종료 전에 확인한다.
