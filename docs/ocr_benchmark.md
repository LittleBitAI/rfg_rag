# OCR 엔진 비교와 320개 이미지 실행 결과

이 문서는 이미지 유형마다 OCR 엔진을 골라 320개 이미지를 처리한 과거 기록입니다. 수치는 당시 로컬 기록을 옮긴 것이며, 이번에 다시 측정하지 않았습니다.

- 정답 텍스트를 직접 만든 이미지 55개로 세 엔진을 비교해, 표와 글은 Gemini(gemini-3.5-flash-lite), 도식은 GPT(gpt-6-luna)를 채택했습니다.
- 로컬 PaddleOCR-VL-1.5는 세 유형 모두 핵심어 재현율이 가장 좋은 API보다 29~53%p 낮아 채택 기준을 넘지 못했습니다.
- 예상액을 보여 드리고 승인받은 뒤 320개 이미지를 모두 처리했습니다. 391개 위치 모두 빈 출력이 없습니다.
- 비교와 전체 실행을 합친 유료 호출은 375회, 비용은 $0.4929609입니다.

## 입력

라벨은 `1` 꼭 읽어야 함, `2` 읽어야 하지만 어려움, `3` 읽을 필요 없음입니다([OCR 화면](ocr_screens.md)).

- 라벨 파일 `data/ocr_labels/ocr_labels_batch1.jsonl`부터 `batch5`까지 `frontend.ocr_select.merge.merge`로 합쳤습니다. 같은 위치를 여러 번 매긴 기록까지 1,046행이며, 같은 위치는 가장 늦게 매긴 라벨을 씁니다.
- 문서에서 꺼낸 이미지 위치는 1,044곳이고, 라벨이 있는 곳은 1,040곳, 없는 곳은 4곳입니다.
- OCR 대상(라벨 1·2)은 391곳, 서로 다른 이미지 320개입니다. 그중 80곳은 HWP 본문에 위치 표시가 없습니다.
- 라벨 3인 649곳과 라벨이 없는 곳은 OCR을 하지 않았습니다.

## 정답 텍스트 55개

320개 이미지를 번호를 붙인 모아보기 이미지 27장으로 모두 보고 유형을 나눴습니다. 서식이나 행·열이 중심이면 표, 문장·메뉴·표지판의 글자가 중심이면 글, 연결·차트·지도·구성 관계가 중심이면 도식입니다. 표 150개, 글 20개, 도식 150개입니다.

처음 준비한 18개에, 사용자가 정한 대로 그룹당 최대 10개 범위에서 40개를 더해 정답 텍스트를 만들었습니다. 이 58개 중 손글씨 본문 일부를 확실히 읽지 못한 3개는 엔진을 돌리기 전에 뺐습니다. 불완전한 정답과 더 잘 읽은 엔진 출력을 비교하면 점수가 왜곡되기 때문입니다. 이 3개도 320개 전체 실행에는 들어갑니다.

최종 55개는 표 20개, 글 15개, 도식 20개입니다. 표와 도식은 라벨 1과 2에서 10개씩, 글은 라벨 1에서 5개, 라벨 2에서 10개를 골랐습니다.

- 엔진 출력을 보기 전에 원본 크기로 이미지를 보고 정답 텍스트와 핵심어를 적었고, 사람이 따로 고치지는 않았습니다.
- 읽을 수 없는 서명은 추측하지 않았습니다. 확정한 55개에는 `[판독불가]` 표시가 없지만, 배경의 아주 작은 글씨나 가려진 서명처럼 읽기 어려운 부분은 이미지별 메모로 남겼습니다. 측정 전부터 알던 한계이며, 점수를 본 뒤 빼거나 넣지 않았습니다.
- 정답 파일의 SHA-256 `3fcb71d4fa9d457d92824b83777c2c2d9dbcb48683eeba8bee94d19e826cc892`를 측정 전에 고정했습니다. `.gitattributes`가 줄 끝을 그대로 지켜, Windows와 Linux에서 받아도 해시가 같습니다.
- 작은 표본이라 320개 전체의 신뢰구간이나 일반적인 OCR 성능은 말할 수 없습니다.

## 지표와 채택 규칙

`rag/preprocessing/ocr_benchmark.py`가 표준 라이브러리로 계산합니다.

- 편집 유사도: 유니코드 정규화(NFC), 대소문자 통일, 연속 공백 한 칸 맞춤을 한 뒤 `1 − 편집 거리(Levenshtein) / 정답 글자 수`로 계산합니다. 출력이 정답보다 훨씬 길면 음수가 될 수 있고, 음수도 0으로 자르지 않고 그대로 평균합니다.
- 핵심어 재현율: 정답 핵심어 중 출력에 단어 단위로 그대로 나온 비율입니다.
- 핵심어 정밀도: 출력에 나온 숫자·영문 코드, 핵심어를 이루는 단어, 정답에 없는 단어 중에서 정답 텍스트에 있는 단어의 비율입니다. 정답에 없는 숫자, 코드, 이름을 지어내면 낮아집니다.
- 뜻은 판정하지 않으므로 띄어쓰기나 조사 차이도 오차가 될 수 있고, 표 칸이나 화살표 관계는 따로 평가하지 않습니다.
- 빈 출력은 공백을 뺀 글자가 하나도 없는 경우입니다.
- 시간은 API는 요청부터 응답까지, PaddleOCR는 초기화를 뺀 이미지당 초로 잽니다. PaddleOCR는 달러 비용이 없습니다.

모델과 유형마다 이미지별 값을 평균합니다. API 모델은 재현율, 정밀도, 낮은 비용 순으로 가장 좋은 모델을 고릅니다. PaddleOCR의 재현율이 그 모델보다 5%p 안쪽으로만 낮고 정밀도가 낮지 않으면 그 유형은 PaddleOCR를 씁니다. 그렇지 않으면 가장 좋은 API 모델을 씁니다.

API 사용 기록의 새 265행과 결과의 모델, 이미지 해시, 비용을 대조했습니다. 표 150개와 글 20개는 Gemini, 도식 150개는 GPT가 처리했습니다. 빈 출력은 이미지 320개 중 0개, 위치 391곳 중 0곳입니다.

## 실행 방법

### API

- 두 API는 같은 지시문(`INSTRUCTION`)과 PNG 이미지를 씁니다.
- Gemini는 기존 `openai` 패키지로 OpenAI 호환 주소 `https://generativelanguage.googleapis.com/v1beta/openai/`를 부릅니다.
- 환경 변수나 `.env`에 `OPENAI_API_KEY`, `GEMINI_API_KEY`가 있어야 합니다. 실행 전에 답변을 만들지 않고 모델 목록만 불러와 두 모델에 접근할 수 있는지 확인했습니다.
- `run_api`는 응답마다 `record_usage`로 `artifacts/api_usage.csv`에 비용을 더하고, 해시, 엔진, OCR 텍스트, 시간, 종료 이유를 결과 파일에 덧붙입니다.
- 자동 재시도는 끄고, 이미 저장된 이미지·엔진 조합은 다시 부르지 않습니다.

### PaddleOCR

- 프로젝트 `.venv`가 아닌 별도 환경에서 `tools/paddle_ocr.py <manifest> <image_dir> <output.jsonl>`을 실행합니다. 프로젝트 환경에는 paddle을 설치하지 않습니다.
- [공식 파이프라인](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/PaddleOCR-VL.html)의 `PaddleOCRVL(pipeline_version="v1.5")`를 씁니다. 이 파이프라인은 지시문을 따로 받지 않아 내장 인식 기능을 씁니다.
- 입력이 이미 잘라 낸 이미지이므로, 페이지 분석을 끄고(`use_layout_detection=False`) 이미지 전체를 기본 `ocr` 기능에 넘깁니다.
- 인식 결과(`parsing_res_list`의 `block.content`)를 저장하고, HTML 표가 나오면 태그 속성을 빼고 행과 칸의 글자로 바꿉니다. 이 정리 시간은 측정에서 뺍니다.
- 출력에는 `seconds`와 `cost_usd: null`을 저장합니다.

### PaddleOCR 환경을 정한 과정

- 처음에는 팀 VM `codeit`에 Python 3.12.3 환경을 만들었습니다. 그런데 디스크 77 GB 중 74 GB가 차 약 2.6 GB만 남았고, CUDA 12.6용 PaddlePaddle 3.2.1은 GPU 설치 파일만 1,890.5 MB였습니다. 승인받아 pip 캐시와 이전 VS Code 서버 3개를 지워 약 3.34 GiB를 더 비웠지만(정리 뒤 여유 5.83 GiB), 압축을 푼 크기만 3.01 GiB이고 CUDA 라이브러리도 따로 필요했으며 메모리 여유도 1 GiB가 안 됐습니다. 그래서 설치만 멈추고 내려받은 파일은 남겼습니다. 다른 팀원의 GPU 작업, Hugging Face의 KURE-v1 캐시, 실행 중인 VS Code 서버, 확장 설치 캐시는 건드리지 않았습니다.
- 그 뒤 사용자가 이 Windows PC에서 직접 실행하기로 정했습니다. 이 PC는 RTX 3080 10 GiB, 메모리 64 GiB이고, 당시 메모리 약 23.8 GiB와 C: 드라이브 약 88 GiB가 비어 있었습니다. 별도 환경에 PaddlePaddle GPU 3.2.1, PaddleOCR 3.7.0, PaddleX 3.7.2를 설치하고 공식 PP-DocLayoutV3와 PaddleOCR-VL-1.5 가중치를 받았습니다. CPU로 한 번 초기화한 뒤 GPU에서 55개를 처리했습니다.
- 공식 Windows 설치 파일은 cuDNN 9.9로 빌드됐는데 의존성은 9.5.1.17을 깔아 경고가 났습니다. 별도 환경의 `nvidia-cudnn-cu12`를 `9.9.0.52`로 바꿔 경고를 없앴습니다. 다시 설치할 때는 GPU 설치 파일과 OCR 패키지를 먼저 설치한 뒤 cuDNN을 직접 덮어써야 합니다. 같은 경고는 [Paddle 공식 이슈 #79388](https://github.com/PaddlePaddle/Paddle/issues/79388)에도 있습니다. cuDNN 9.5로 돌린 결과는 모두 집계에서 뺐습니다.
- 페이지 분석 기본값은 이미지 영역의 글자를 읽지 않아, 서식 화면에서 글자 대신 이미지 링크를 돌려줬습니다. 이미지·차트·직인 인식을 켜도 서식 일부를 빠뜨렸고, 도식 하나에 376.31초가 걸리면서 공유 GPU 메모리를 약 2.5 GiB 썼습니다. 그래서 페이지 분석을 끄고 55개 모두 이미지 전체 OCR로 다시 돌렸습니다. 페이지 분석으로 돌린 결과도 모두 집계에서 뺐습니다. 정답, 핵심어, 지표, 채택 규칙은 바꾸지 않았고 API도 다시 부르지 않았습니다.
- 이미지마다 쓰지 않는 GPU 캐시를 비우도록 설정을 고정했습니다. 이 설정 전에 잰 14개는 모두 다시 재서 바꿨고, 품질이 좋아진 것만 골라 넣지 않았습니다. 최종 55개는 모두 같은 설정입니다.
- 처음에는 GPU 여유가 약 1.8 GiB뿐이었습니다. 웹 서버 프로세스가 저절로 끝나 약 4.6 GiB가 됐고, 사용자 승인을 받아 KURE 색인을 들고 있던 `02_retrieval.ipynb` 커널만 정상 종료해 8,346 MiB가 됐습니다. 저장된 노트북과 색인 파일은 바뀌지 않았습니다.

## 01 전처리에 넣기

`summarize`는 세 엔진 모두 같은 정답 이미지의 결과가 있어야 집계합니다. `winners`로 유형별 채택 엔진을 정하고, `caption_rows`로 결과를 위치별로 펼쳐 `data/ocr_captions.jsonl`을 만듭니다. 01 전처리는 이 파일을 API 호출 없이 읽어 이렇게 넣습니다.

- HWP는 원래 본문 위치(`marker_start`)에 넣고, 위치 표시가 없는 곳은 문서 끝에 넣습니다.
- PDF는 그 쪽에서 이미지 위에 있는 글자 위치를 찾아 본문을 나눠 넣고, 같은 위치는 이미지 순서(`image_index`)대로 넣습니다.
- 결과 파일이 있을 때만 위치를 지키는 청크 방식을 씁니다. 본문, 표, 그림 순서대로 청크를 만들고, 그림 때문에 짧아진 본문이나 짧은 OCR 텍스트도 버리지 않습니다. 표 청크는 기존 최소 길이(`min_chunk_chars`)를 그대로 씁니다.
- 결과 파일이 없거나 그 문서에 OCR 텍스트가 없으면 기존 청크 순서와 최소 길이 규칙을 그대로 씁니다.
- 저장된 HWP 이미지의 해시가 다르면 멈춥니다. 청크의 키는 기존 형식 그대로입니다. 기존 공백·한자 정규화는 OCR 텍스트에도 똑같이 적용됩니다.

확인한 내용입니다.

- 결과 파일이 없을 때 98개 문서의 17,614개 청크가 기준 커밋 `58b8b15`와 모두 같았습니다.
- 유료 OCR 대신 번호를 붙인 가짜 텍스트를 넣어, 79개 문서의 391곳(HWP 위치 표시가 없는 80곳 포함)이 모두 들어가고 개수와 중복 횟수가 위치 목록과 같음을 확인했습니다. 최종 청크 순서와 문서 끝 80곳도 맞았고, 모든 청크는 기존 10개 키만 가졌습니다.
- 실제 OCR 텍스트를 넣고 `01_preprocessing.ipynb`의 코드 셀을 그대로 실행했습니다. 출력 폴더만 따로 둬 공용 `chunks.jsonl`, `docs.jsonl`을 덮어쓰지 않았습니다. API 키를 빼고 네트워크와 OCR 클라이언트를 막았으며, API 사용 기록도 전후 같았습니다.

| 01 실행 조건 | 문서 | 전체 청크 | OCR 레코드 | OCR 청크 | 확인 |
|---|---:|---:|---:|---:|---|
| 저장된 OCR 텍스트 사용 | 98 | 22,108 | 391 | 846 | 순서, 텍스트별 위치 수, 기존 키가 맞고, HWP 위치 표시가 없는 80곳은 문서 끝 |
| 설정한 경로에 OCR 파일 없음 | 98 | 17,614 | 0 | 0 | 기준 커밋 `58b8b15`의 모든 청크와 같음 |

긴 텍스트는 기존 700자 분할 규칙으로 여러 청크가 되어, 391개 레코드에서 846개 청크가 나옵니다. OCR 텍스트가 없는 19개 문서의 청크는 결과 파일이 있어도 기준 커밋과 같았습니다. 전체 청크가 늘어난 것은 본문, 표, 그림 순서를 지키느라 본문을 나누고 짧아진 조각도 남겼기 때문입니다. 당시 전체 테스트 1,065개가 통과했습니다. 02 색인, 03·04·05, 골든 정답 청크는 바꾸거나 실행하지 않았습니다.
