## What the tokenizer does today

`KiwiTokenizer` in `rag/retrieval/indexing.py` produces the BM25 tokens for both the chunks and the query. It:
- runs default `Kiwi()` and keeps nouns, verb and adjective stems, foreign words, Hanja, numbers and general adverbs;
- keeps the negations `않` and `아니`;
- adds a Hangul reading for each Hanja token;
- appends requirement codes such as `sfr-001` as extra tokens;
- uses a user dictionary of 7 words (`지체상금`, `부가가치세`, `하자보수`, `과업지시서`, `제안요청서`, `기술협상`, `공동수급`) and one alias (`부가세` → `부가가치세`). Spaced-out forms of these words are joined before analysis.

The last real change to this logic was the PR #21 port of the search lead's `feature/Retrieval` work. Since then it has only been carried along. BM25 itself uses `k1=1.5` and `b=0.75` and gets 40% of the fused score (`dense_weight: 0.6`).

## Gaps the code and probe show

I ran the current tokenizer on sample RFP phrases:

| Input | Tokens | Problem |
|---|---|---|
| `개인정보보호 및 정보보안 요구사항` | `개인, 정보, 보호, 및, 정보, 보안, 요구, 사항` | The compound is fully split and no joined token is kept, so a phrase match scores like scattered words. `및` survives as an adverb. |
| `ISMS-P 인증과 GS인증 1등급` | `isms, p, 인증, gs, 인증, 1, 등급` | Hyphenated certification names break apart. The code regex only catches 2–5 letters plus 2–4 digits. |
| `전자정부표준프레임워크 3.10 적용` | `전자정부 표준프레임워크, …` | Kiwi's built-in dictionary emits one token that contains a space. A query that spells it differently may never match it. |
| `이 사업은 하지 않는다` | `사업, 하, 않` | Light verbs like `하` are kept as noise. |
| `하자보수 기간과 지체상금률` | `하자보수, 기간, 지체상금` | The user dictionary works here, but it covers only 7 hand-picked words. Agency and project names from the router's agency list never reach BM25. |

Some other gaps:
- **Unpinned version:** `requirements.txt` allows `kiwipiepy>=0.20` while this PC has 0.24.0. Kiwi's documentation doesn't promise identical analyses across versions, so the team VM's index can differ from yours.
- **Second Kiwi instance:** the quantity parser runs its own default `Kiwi()` with no user words. In a review round it analysed `인 전체 사업` as three general nouns, which broke project recognition. It's a separate instance from BM25's, but it shares the same version exposure.
- **Untried options:** no Kiwi model-type or typo-correction settings are used. I haven't checked whether 0.24 offers anything useful there.

## What the measurements say

The only number on record comes from the 30-question dev sample, scored at chunk level on the 15 questions whose evidence is fully chunk-labelled. Each value is the average per-question share of gold chunks found in the top k:

| Component | Recall@5 | Recall@10 | Recall@20 |
|---|---|---|---|
| BM25-only | 0.567 | 0.667 | 0.733 |
| Dense-only | 0.700 | 0.867 | 0.933 |
| Fused | 0.667 | 0.800 | 0.867 |

At document level everything scores 1.0, because agency routing does that work. So BM25 trails dense and fused trails dense-only. That suggests BM25 is holding the fusion back. But 15 questions is too few to call, and the gap can't yet be blamed on the tokenizer rather than BM25 itself or the 0.6 weight.

To answer "is it advanced enough", run the same retrieval-only check with tokenizer variants. Rebuilding the index and the existing `rerun_retrieval` path cost nothing in API calls. The catch is that only 30 dev questions have stored rewrites, and getting more needs paid rewriting.
