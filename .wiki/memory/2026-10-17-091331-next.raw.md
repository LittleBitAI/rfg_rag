## 답 · 2026-10-17 07:31 · unverified

This is doable with no new parsing and no new packages. The OCR results already exist, and so do the images they came from and a Markdown renderer.

What's already there
- The parsed text. `data/ocr_captions.jsonl` has the 391 transcriptions that #61 linked into preprocessing, one per place an image appears. They cover 320 distinct images: 342 places in HWP files and 49 in PDFs. Each row records the document and its position, the engine (`gpt-6-luna` for 211 diagrams, `gemini-3.5-flash-lite` for 160 tables and 20 text images) and the text. None of the 391 texts is empty.
- The original images. Every one of the 391 places has a viewable image in `artifacts/ocr_labels/images/`. Both files use the same `image_sha256`, so the left pane needs no re-extraction. The labeller's server on port 8766 already serves these images.
- The rendering. The OCR text is Markdown, with headings, bullet lists and `|` tables in 207 of the 391. `react-markdown` and `remark-gfm` are already in `frontend/web/package.json`, so the right pane can show real tables and lists instead of a raw string.
- The menu slot. The top-right settings menu in `frontend/web/src/App.jsx` holds one link, `OCR 이미지 라벨링` (OCR image labelling) to `/ocr.html`. The review screen would be a second link under it, pointing to a new Vite page next to `ocr.html`.

Limits to know
- Older captions can't be paired with images. `artifacts/captions.jsonl` (444 rows) holds older captions from the `OCR = True` path. They are keyed only by a 16-character hash, with no document or position, so they can't be matched to an image. I'd leave them out.
- Only images have an "original" to show. PDF tables extracted by `pdfplumber` and plain HWP body text weren't OCR'd, so there's no original image for them. This screen covers image-to-text only.
- Preprocessing stays untouched. The screen only reads the captions file and changes nothing in `rag/`, which keeps the frontend's "shell over the backend" rule.

## 답 · 2026-10-17 07:37 · unverified

Nothing in this screen calls an API. The image and its text were already paired when OCR ran, so the screen only reads two local files: the 391 saved transcriptions in `data/ocr_captions.jsonl` and the images already extracted to `artifacts/ocr_labels/images/`. Your verdicts are the only thing it writes, and they go to a local file. 01 already reads the same captions file without an API key or any call, and this screen follows that rule. None of the navigation options I offered would have called an API. They only differed in how you move between cards. I've written "no API calls" into the done conditions so the reviewer checks it.

One card per image works without losing anything. Of the 320 images, 20 appear in more than one place, and each of those has the same text, engine and image type in every place. So a card shows the text once and lists all the places the image appears. Each verdict is saved against the image, so one verdict covers every place that image appears.

You didn't pick a navigation option, so the spec uses the one I recommended:
- filters for document, image type, engine and verdict status (so "not reviewed yet" can be shown on its own)
- previous/next buttons, also on the arrow keys

If you'd rather have the scrolling list or the raw-text toggle, say so and I'll update the spec before the work starts.
