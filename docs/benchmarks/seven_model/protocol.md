# 임베딩 모델 검색 비교 규약

일곱 임베딩 모델의 검색 성능을 비교할 때 지킨 규칙입니다. 최신 결과는 [문맥 앵커 재측정](anchor/report.md)에 있고, 용어는 그 문서의 [용어 표](anchor/report.md#용어)를 따릅니다.

실제 질문·정답·근거와 검색된 본문은 공유하지 않는 로컬 폴더 `artifacts/`에만 둡니다. 저장소에는 문항 수, 점수, 응답 시간, 자원 사용량 같은 집계 값과 그 값을 다룬 보고서만 올립니다. 파일 형식이 JSONL이 아니어도 실제 기록이 들어 있으면 올리지 않습니다. 저장소 테스트에는 직접 만든 가상 데이터만 씁니다.

## 바꾸지 않는 것

- 서비스의 모델, 색인, 설정, Kiwi 규칙과 사전은 그대로 둡니다.
- 유료 API(질문 재작성, 답변, 채점, OCR), 유료 컴퓨팅, test 분할은 쓰지 않습니다.
- 후보 모델을 더하지 않고, 파인튜닝, 리랭커(검색 결과 재정렬 모델), 새 청킹, 모델 가중치 양자화(압축), CPU offload(일부 계산을 CPU로 넘기기)도 쓰지 않습니다.

## 비교 방법

1단계는 KURE로 고정하고 검색 방법 다섯 가지(띄어쓰기 단어 검색, 의미 검색, Kiwi 단어 검색, Kiwi + 의미, 띄어쓰기 + 의미)를 비교합니다. 띄어쓰기 단어 검색은 형태소 분석 없이 띄어쓰기로만 단어를 나눕니다(`str.split()`). BM25 설정은 `k1=1.5`, `b=0.75`입니다. 2단계는 일곱 모델마다 의미 검색과 Kiwi 하이브리드를 비교하고, KURE는 1단계 결과를 그대로 씁니다.

두 단계 모두 기관 필터와 기관별 교차 배치는 그대로 둡니다. 실험 경로는 요구사항 번호 우선 배치와 수량 필터를 끄고, 서비스 경로는 번호 우선 배치, 수량 필터, 중복 제거, 2,500토큰 담기를 서비스와 똑같이 켭니다. 수량 필터를 탄 질문은 일반 순위와 따로 보고합니다. 후보 50개, 지금의 점수 합치기 방식(min-max), 수량 설정, 2,500토큰 예산도 바꾸지 않습니다. 2,500토큰은 모든 모델에서 같은 KURE 토크나이저로 세고, 임베딩을 만들 때는 각 모델의 토크나이저를 씁니다.

## 문항과 정답 청크

dev 원본, 말뭉치, 설정, 근거는 한 글자도 바꾸지 않고, 각 파일의 해시(파일 내용을 확인하는 값)를 로컬 기록(manifest)에 남깁니다. 검색 평가에는 dev 전체를 씁니다. 답변 채점에만 필요한 핵심 사실(`key_facts`)이 없다는 이유로 질문을 빼지 않습니다.

정답 청크는 아래 규칙으로 다시 찾습니다.

1. 근거 문장이 같은 문서의 청크 하나에만 그대로 들어 있으면 그 청크를 정답으로 정합니다.
2. 근거가 짧거나 여러 청크에 들어 있으면, 같은 근거 묶음의 다른 20자 이상 문장이 함께 든 청크가 하나뿐일 때만 정답으로 정합니다. 이것을 문맥 앵커라고 부릅니다.

근거 일부만 정답 청크가 정해진 질문은 청크 채점에서 뺍니다. 일부만 맞힌 것을 정답 전체로 채점하지 않기 위해서입니다.

## 튜닝과 검증 분할

점수를 계산하기 전에 시드와 질문 번호로 튜닝·검증 분할을 정해 로컬에 저장합니다. 같은 질문이 겹치거나 정답 청크·생성 묶음을 함께 쓰는 질문은 같은 분할에 넣고, 주제별 균형과 남은 중복 가능성을 보고서에 적습니다. 이 dev를 이전 개발에서 이미 봤다면 그것도 적습니다. 검증 분할은 가중치를 고르는 데 쓰지 않으며, 최종 test 결과라고 부르지 않습니다.

하이브리드는 의미 검색 가중치 0.6으로 먼저 잰 뒤, 0.2, 0.4, 0.6, 0.8 중에서 하나를 고릅니다. 기준은 튜닝 분할에서 일반 경로를 탄 청크 채점 대상 질문의 평균 R@10입니다. 점수가 같으면 0.6에 가까운 값, 그다음 낮은 값을 고릅니다. 고른 값을 파일로 저장한 뒤에 검증 분할을 채점하고, 저장한 값이 바뀌면 집계를 멈춥니다.

## 실행 방법

앱 환경을 건드리지 않도록 별도 가상환경 `.venv-benchmark310`에 CUDA PyTorch와 `requirements-benchmark.txt`를 설치합니다. 모델은 미리 내려받고, 측정 중에는 Hugging Face를 오프라인 모드로 두고 네트워크 연결을 막습니다. RTX 3080 10 GiB에서 남은 GPU 메모리와 디스크를 확인한 뒤, 모델마다 새 프로세스로 하나씩 실행합니다. 상관없는 프로그램은 끄지 않습니다.

측정 코드를 먼저 커밋한 뒤 준비 단계를 실행합니다. 준비 단계는 그 커밋과 검색·검증·지표 코드의 해시(SHA-256)를 manifest v3에 고정합니다. 커밋하지 않은 코드 변경, 준비 뒤의 새 커밋, 모델마다 다른 코드 해시가 있으면 실행·집계·검증을 거부합니다. 코드 해시가 없는 예전 기록에 지금 해시를 붙여 같은 실행으로 취급하지 않습니다.

```powershell
.venv-benchmark310\Scripts\python -m rag.validation.local_inputs
.venv-benchmark310\Scripts\python -m rag.retrieval.benchmark prepare
foreach ($model in @('kure','nemotron','harrier','jina','pplx','dragonkue','upskyy')) {
    .venv-benchmark310\Scripts\python -m rag.retrieval.benchmark run --model $model
    if ($LASTEXITCODE -ne 0) { throw "Benchmark failed: $model" }
}
.venv-benchmark310\Scripts\python -m rag.retrieval.benchmark summarize
```

입력과 측정 결과는 `artifacts/seven_model_anchor/`에, 고정한 질문·분할·manifest와 집계·문항별 결과는 그 아래 `record/`에 저장합니다. 끝난 측정은 덮어쓰지 않습니다. 단어 검색 사례 분석을 다시 하려면 로컬 파일 `audit_probes.json`에 살펴볼 질문 번호를 적고 `python -m rag.retrieval.benchmark.audit`를 실행합니다. 실제 질문 번호는 코드에 넣지 않습니다.

평가 입력은 공통 로더가 `artifacts/local_inputs/`에서 읽습니다. 파일이 없으면 Git에서 추적을 끊기 직전의 로컬 기록에서 되살리며, 네트워크는 쓰지 않습니다. 얕은 clone처럼 그 기록이 없으면 담당자에게 받은 비공개 묶음을 `python -m rag.validation.local_inputs --from-directory PATH`로 먼저 복원합니다. 묶음의 구조와 검사 규칙은 [평가 문서](../../evaluation.md#로컬-평가-입력과-ocr-캡션-복원)에 있습니다.

## 응답 시간과 자원

설정마다 예열을 뺀 뒤, 질문 순서를 섞어 세 번 잽니다. 질문은 하나씩 넣고 질문 임베딩은 캐시하지 않습니다. 질문을 넣은 때부터 답변 모델에 넘길 근거가 나올 때까지를 GPU 작업이 끝나기를 기다려 잽니다. 모델 불러오기, 색인 만들기, 지표 계산 시간은 넣지 않습니다. 밀리초 원래 값, p50/p90, 표본 수, 회차별 차이와 단계별 시간·처리량·색인 크기·최대 메모리를 로컬에 기록합니다. GPU 전체 사용량에는 다른 프로그램이 포함되고, 일정 간격으로 잰 메모리는 짧은 순간의 최댓값을 놓칠 수 있습니다.

## 지표와 추천

- 문서·청크 Recall@5/10/20과 MRR@5/10/20은 2,500토큰 담기 전 순위로 계산하고, 같은 문서를 먼저 합치지 않습니다.
- 요구사항 번호 포함 비율은 순위와 상관없이 따로 세는 지표입니다.
- Coverage와 full은 2,500토큰 담기 뒤에 근거가 하나인 질문과 여러 개인 질문을 나눠 계산하고, 채점 대상과 제외 문항 수를 모두 적습니다.
- dev 전체 집계는 참고 값으로 따로 표시합니다.
- 추천은 Kiwi 하이브리드의 검증 분할 청크 R@10을 먼저 보되, R@20, 근거 여러 개 질문, 주제별 하락, p90, 메모리, 라이선스를 함께 따집니다. 점수만으로 모델을 자동으로 고르지 않습니다.

## 기록 확인

모델 완료 기록에는 모든 설정의 결과 파일과 응답 시간 파일의 이름과 해시를 남깁니다. 집계는 점수를 계산하고 가중치를 고르기 전에 모든 모델의 코드 해시와 파일 해시를 확인합니다. 결과를 고친 뒤 점수를 다시 계산해도 해시가 다르면 거부합니다. 내보낼 때는 결과, 응답 시간, 완료 기록을 그대로 복사하고, 내보낸 기록도 같은 방법으로 확인합니다. 원래 기록에 점수를 다시 써 넣지 않습니다.

완료할 때 해시를 남기지 않은 예전 측정은 그대로 과거 기록으로 두고, 검증을 통과했다거나 지금 추천의 근거라고 표시하지 않습니다. 나중에 해시를 만들어도 당시 파일이 그대로였다는 증명은 안 되므로, 확정하려면 새 커밋에서 다시 재야 합니다.

집계 단계에서는 분할, 세 회차 순서, 모델 완료 상태, 고른 가중치를 다시 확인하고, 지표는 기존 검색 지표 함수로 계산합니다. 저장소 테스트는 가상 데이터와 일부러 망가뜨린 사례만 씁니다. `eval/golden/`의 원본은 Git에 올리지 않고 로컬에만 두며, 실제 dev 문항을 테스트에 쓰지 않습니다.
